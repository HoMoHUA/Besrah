# Opt-in Web Push reminder (not deployed)

This feature is off unless **all** values below are present and valid, the SQLite directory is private and writable, and the journey beta is enabled. Set these through the service's private environment mechanism; never commit keys or endpoint URLs:

- `BESRAH_WEBPUSH_PUBLIC_KEY` and `BESRAH_WEBPUSH_PRIVATE_KEY`: matching URL-safe base64 P-256 VAPID keypair, generated privately with `npx web-push generate-vapid-keys` from `packages/core`. Protect the private key like a password; rotate deliberately (rotation invalidates old subscriptions).
- `BESRAH_WEBPUSH_SUBJECT`: contact in `mailto:address@example.org` format.
- `BESRAH_WEBPUSH_DB`: absolute database path under a service-owned, mode-0700 directory. The database is mode 0600. Do not share the directory with other users, expose it over HTTP, or put it in a public backup.
- `BESRAH_ALLOWED_ORIGINS`: comma-separated exact HTTPS origins, e.g. the canonical Besrah origin (not a path or wildcard).
- `BESRAH_JOURNEY_BETA=on` and the existing beta controls, with normal calendar caveats.

The supplied `deploy/nginx/besrah-webpush-post.conf` is a **candidate** snippet, not an instruction to reload production: exact POST locations are necessary because the existing generic `/api/` location denies POST. Validate in an isolated nginx config and obtain explicit deployment authorization before applying it. The existing generic API GET location serves `/api/reminders/config`.

## Behaviour and limits

A user selects an actual returned model event and explicitly presses its reminder button; PushManager requests permission. The server re-plans and matches the event identifier, origin, destination and departure against the current model. It accepts departures 6 minutes to 7 days ahead and queues a single reminder 5 minutes before departure. A device may have one pending reminder; replacing it first deletes the old one. Stored subscription data and a hash of a random cancellation token are deleted on claim, expiry, or cancellation; while the service is down, expiry cleanup happens when it restarts. A maximum of 1,000 reminders and per-client/global admission limits bound storage and compute. A durable cancellation tombstone (token hash only) persists for 7 days plus 60 seconds to prevent a delayed create after cancellation, including across restarts. Tombstones are capped at 10,000, with 1,000 slots reserved for cancellation of already-queued reminders; when capacity is exhausted cancellation may fail and must be retried. Expired tombstones are purged during scheduler ticks or later use. Create and cancellation have separate 60/min global and 6/min per-client budgets; these do not prevent a distributed attacker from filling the shared queue. Each reminder has a one-minute send window and push-service TTL of 60 seconds. The generic notification includes no stations, direction or travel time. Before the create response is confirmed, the exact request (subscription endpoint and keys, line, origin, destination, event identifier, departure and cancellation token) is held in local storage to recover an ambiguous response. Once confirmed, only the cancellation token and expiry remain. Pending records may remain if the user does not return; expiry cleanup occurs only on the next use of the reminder feature. Existing confirmed records are compacted on next use. If local storage is cleared, cancellation by this UI is no longer possible, but the queued record still expires.

Delivery is **at most one attempt**, not guaranteed: the scheduler removes the record before attempting delivery; outages, DNS failures, process crashes, expired windows and push-service rejection can lose it. Cancellation cannot recall an already claimed/in-flight push. Users can cancel from Profile on the same device even when planner preparation fails; this removes the server reminder, but does not unsubscribe an unprepared browser. Planner cancellation also attempts to unsubscribe. The scheduler runs up to 10 workers. Admission rejects new reminders when 10 queued reminders are already due within 59 seconds on either side; this conservative bound fits the 60-second window under normal operation (bounded DNS and send total at most 8 seconds), but process outages or stalls can still cause expiry. Sanitized aggregate attempted, missed, accepted, rejected and failed counts go to stderr; scheduler failure emits a fixed message and disables the feature. No subscription or journey data is logged. The service worker has no fetch handler and creates no offline cache. iOS support depends on an installed Home Screen web app and actual platform permission; Telegram WebViews may not support Web Push. A real device delivery test is still required.

Outbound push hosts are restricted to FCM, Mozilla and bounded `*.push.apple.com`, HTTPS port 443 only. All DNS answers must be public and the connection uses a pinned validated address with TLS hostname verification; redirects are not followed. Never log endpoint URLs or subscription keys. The scheduler is single-process; do not run multiple independent instances against one database without further coordination and operational review.

References: Apple Developer, “Sending web push notifications in web apps and browsers”; MDN, “PushManager: subscribe() method.”
