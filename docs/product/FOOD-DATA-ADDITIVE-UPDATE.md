# بسفود — سیاست به‌روزرسانی افزایشی و معیارسنجی داده‌های موجود

**هدف:** منبع فعلی `research/vendors.sqlite` (اسنپ‌فود و تپسی‌فود) و ایندکس قبلی دست‌نخورده بمانند. اطلاعات همان منبع دوباره ارزیابی شوند، دسته‌های قبلاً حذف‌شده (گل‌فروشی، کافه، قنادی، نانوایی، سوپرمارکت، میوه و پروتئین و ...) به فهرست اضافه شوند و اصلاحات معتبر در رکوردهای موجود اعمال شود. **هیچ وب‌اسکرپینگ، فید خارجی یا جایگزینی کلی دیتابیس در این مرحله مجاز نیست.**

## حقیقت مهم

- سورس عمومی GitHub نه دیتابیس خصوصی `vendors.sqlite` را دارد و نه کل ایندکس واقعی Production را. از روی تست‌های ساختگی نمی‌توان شمارش واقعی فروشندگان یا پوشش دسته‌ها را تأیید کرد.
- ابزار `build_food_index.py` فقط **کاندیدا** می‌سازد؛ مستقیماً روی مسیر Production اجرا نشود. ابزار `merge_food_index.py` کاندیدا را با ایندکس موجود به شکل شناسه‌محور ادغام می‌کند.
- «به‌روزرسانی» به معنای حذف دیتابیس قبلی نیست. دیتابیس منبع و فایل ایندکس قبلی تغییر نمی‌کنند. خروجی در دایرکتوری خصوصی staging جدید است.
- جست‌وجو/نمایش دسته‌های جدید در برنامه قبلاً کدنویسی شده؛ تا ساخت و استقرار ایندکس غنی‌شده، این فروشندگان لزوماً در اپ ظاهر نمی‌شوند.
- *دسته‌بندی فروشنده* با *ترجیح کاربر* متفاوت است. مدل ساعت و موقعیت، مجاز به استنباط تولد، نیت خرید هدیه، بازبودن فعلی فروشگاه، هزینه ارسال یا موجودی نیست.

## جریان اجرایی امن روی سرور (فقط بعد از تأیید مسیرهای واقعی)

1. از مسیر واقعی `research/vendors.sqlite` و ایندکس فعلی فقط نسخه پشتیبان امن تهیه کنید و SHA-256 آن‌ها را ثبت کنید. از طریق مسیر عمومی وب یا GitHub، داده خام منتشر نشود.
2. یک دایرکتوری staging خصوصی و تازه روی دیسک با فضای کافی بسازید. اگر دیسک محدود است، **پیش از تولید** متوقف شوید.
3. از **همین دیتابیس موجود** خروجی بازسازی‌شده بگیرید:

```bash
python3 scripts/food/build_food_index.py \
  --db /PRIVATE/PATH/research/vendors.sqlite \
  --research /PRIVATE/PATH/research \
  --out /PRIVATE/STAGING/candidate
```

4. ارزیابی بدون نوشتن:

```bash
python3 scripts/food/merge_food_index.py \
  --baseline /PRIVATE/CURRENT/food-index-v1.json.gz \
  --candidate /PRIVATE/STAGING/candidate/food-index-v1.json.gz \
  --dry-run
```

5. درصورت نبود تضاد و با استفاده از **دایرکتوری خروجی کاملاً خالی و مجزا**:

```bash
python3 scripts/food/merge_food_index.py \
  --baseline /PRIVATE/CURRENT/food-index-v1.json.gz \
  --candidate /PRIVATE/STAGING/candidate/food-index-v1.json.gz \
  --out /PRIVATE/STAGING/enriched
```

6. **پیش از هر استقرار** گزارش `food-merge-report.json`، محتوای فشرده `food-index-v1.json.gz` و در صورت وجود `previous-vendor-versions.json.gz` را بازبینی کنید؛ سطرهای سابق و تاریخ ثبت را با منبع اصلی تطبیق دهید.
7. تست Core و Mini App را با نسخه کاندید و داده خصوصی در **محیط آزمایشی** اجرا کنید. فقط بعد از مجوز مستقل صاحب پروژه و برنامه برگشت، امکان استقرار Production مطرح می‌شود.

## معیارهای پذیرش، قبل از انتشار

| شاخص | انتظار |
|---|---|
| فروشندگان قبلی | هیچ شناسه‌ای حذف نشود؛ شمارش کل فروشندگان کاهش نیابد |
| رستوران، فست‌فود | جست‌وجو و نمایش سابق بدون رگرسیون |
| کافه، قنادی/شیرینی، نانوایی | دسته‌بندی و جست‌وجوی مستقل |
| گل‌فروشی و هدیه | از رستوران جدا و به مقصد واقعی ارائه‌دهنده هدایت شوند |
| سوپرمارکت، میوه، پروتئین، خشکبار | فیلتر مستقل و بدون حذف به عنوان مخلفات غذا |
| قیمت نامعلوم | صفر تومان تلقی نشود |
| قیمت ثبت‌شده | زمان ثبت قدیمی، قیمت لحظه‌ای یا ارزان‌ترین بازار معرفی نشود |
| منابع دو اپ | هر دو source و لینک مرتبط حفظ شوند |
| فروشنده/منوی تازه از همان داده | با شناسه/کلید پایدار اضافه شود؛ ادغام تکراری نباشد |
| داده جدیدتر درباره یک فروشنده | فقط اگر تاریخ ثبت جدیدتر است؛ نسخه قبلی برای بازبینی در staging بماند |
| حذف آیتم منو در داده جدید | **متوقف شود**؛ بدون تصمیم انسانی، حذف یا تغییر نمایش اتفاق نیفتد |
| قیمت متناقض در همان زمان ثبت | **متوقف شود**؛ حدس زده نشود |
| قابلیت‌های پیشنهاد هوشمند | صبح کافه/نانوایی؛ ظهر و شب غذا؛ عصر کافه/شیرینی؛ هدیه صرفاً با نیاز صریح کاربر |
| بازگشت | امکان برگرداندن ایندکس قبل بدون تغییر منبع خام |

### نکته معماری

ایندکس فعلی v1 برای هر فروشنده فقط یک `cap` ثبت می‌کند و زمان مستقل هر آیتم منو ندارد. به همین دلیل، اگر اسنپ‌شات جدید یک فروشنده آیتمی از منوی قدیمی را حذف کند، موتور به‌صورت خودکار قیمت قدیم آن را زیر تاریخ جدید حمل نمی‌کند؛ **ادغام متوقف می‌شود** تا در نسخه بعدی، سیاست آرشیو یا آیتم ناموجود با زمان مستقل طراحی شود. این توقف عمدی، از داده ساختگی جلوگیری می‌کند.

## کارهایی که این Pull Request انجام نمی‌دهد

- هیچ تغییری در داده زنده سرور یا دیتابیس اصلی؛
- هیچ حذف، overwrite یا refresh اجباری قیمت‌ها؛
- هیچ جمع‌آوری جدید از سرویس‌های بیرونی؛
- هیچ تضمین تازه‌بودن قیمت، بازبودن فروشگاه یا موجودی کالا؛
- هیچ Merge به `main` یا استقرار در Production.

**خروجی این تغییر صرفاً ابزار ادغام، گزارش سنجش، تست‌های محافظتی و این دستورالعمل است.**
