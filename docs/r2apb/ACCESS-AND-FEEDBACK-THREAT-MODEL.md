# Threat model: دسترسی Beta و مسیر بازخورد — R2a-PB

نسخه کد: `597b774` (شاخه `feature/r2a-production-beta`). این سند تصمیم های مورد نیاز مالک را مشخص می کند؛ هیچ سیاستی را خودسرانه تغییر نمی دهد.

## ۱. دارایی ها و مرز اعتماد

| دارایی | اهمیت | محل |
|---|---|---|
| دسترس پذیری تابلو، ردیاب، بسفود و بات (سرویس فعلی) | بالا | همان process `besrah-core` (۱۹۲MiB، `TasksMax=64`) |
| صحت جدول مدل شده و عدم ادعای «زنده» | بالا | `transit-journey`، تقویم، متن ثابت UI |
| بازخورد ناشناس (انتخاب ها، ایستگاه، خط، زمان، یادداشت کوتاه) | متوسط (حریم خصوصی) | `/var/lib/private/besrah-feedback/feedback/*.jsonl` (0600) |
| قابلیت اعتماد اندازه گیری دقت | بالا | تفکیک خوداظهاری از مشاهده مستقل |

مرزها: مرورگر/WebView کاربر ← (TLS) Nginx لبه ← loopback `127.0.0.1:3080` ← process هسته ← فایل سیستم. فقط loopback پشت Nginx قابل اعتماد است؛ هیچ داده ای از کاربر قدرت تصمیم ندارد. `userId`/`initData` از مرورگر هرگز authority نیست و کد آن ها را اصلاً نمی خواند (آزموده: B5، ذخیره بدون هویت).

## ۲. تصمیم D1 — سطح دسترسی (مقایسه)

| | **الف) Beta اختیاری عمومی** (کد فعلی) | **ب) آزمونگر محدود با کنترل سمت سرور** |
|---|---|---|
| تعریف | هر بازدیدکننده می تواند وارد بتا شود یا نشود | فقط افراد مجاز |
| کنترل سرور | flag و فایل کنترل (روشن/خاموش کل)، rate limit، مرز نوشتن جدا | نیازمند احراز هویت سرور، چیزی که امروز **وجود ندارد** |
| هزینه ساخت | ندارد | بالا: نگهداری راز (مثلاً توکن بات) داخل هسته که امروز ندارد، یا auth جدا در Nginx |
| ریسک | سطح عمومی بزرگ تر؛ اسپم محتمل | کاربر مجاز بودن را به هم ریخته می کند؛ نشت توکن/لینک |
| صداقت محصول | «Beta اختیاری عمومی» | فقط وقتی واقعاً احراز شود «محدود» نامیده شود |

نکته کلیدی: **روشن کردن flag یعنی کارت ورود برای همه نمایش داده می شود.** `rolloutPercent` فقط تعیین می کند کدام بازدیدکننده «برجسته» شود؛ مانع ورود نیست. لینک `?beta=1` و ذخیره opt-in در مرورگر **پنهان سازی UI** هستند، نه احراز هویت. API فقط خواندنی برای هر کسی که نشانی را بداند در دسترس است و همین طراحی شده.

اگر مالک گزینه ب را بخواهد، روش هایی که می توان بررسی کرد (هیچ کدام ساخته نشده):
1. اعتبارسنجی `initData` تلگرام در سرور (HMAC با توکن بات): نیازمند قرار دادن راز بات در process هسته یا یک سرویس واسط؛ سطح حمله جدید؛ هویت واقعی و محدودیت به حساب ها ممکن می شود. با بازخورد ناشناس سازگار نیست مگر هویت جدا از رکورد نگهداری شود.
2. `auth_request` یا توکن قابل ابطال در Nginx: کم تغییر ولی لینک قابل اشتراک است؛ لینک نشت می کند.
3. پیش نمایش جدا با vhost مستقل برای تعداد کم: بیشترین جدایی، ولی کاربران عادی دیده نمی شوند و آزمون Production واقعی نیست.

**پیشنهاد:** گزینه الف، با برچسب «Beta» و متن «اختیاری». اتکا به «فقط آزمونگران» بدون احراز واقعی ممنوع است.

## ۳. رفتار endpoint ها وقتی خاموش است (با آزمون)

| وضعیت | `GET /app/api/journey` | `POST …/journey-feedback` | `GET /app/api/beta` | API قدیمی |
|---|---|---|---|---|
| env خاموش (پیش فرض) | ۴۰۴ (A2) | ۴۰۴ (A3) | ۲۰۰ با `enabled:false` | ۲۰۰ (A4/A5) |
| `enabled:false` در فایل کنترل (بدون restart) | ۴۰۴ | ۴۰۴ (K1) | `enabled:false` | ۲۰۰، همان PID |
| `feedbackEnabled:false` | ۲۰۰ | **۵۰۳** (K2) | `feedbackEnabled:false` | ۲۰۰ |
| فایل کنترل خراب/حذف/قابل نوشتن برای دیگران/در مسیر ناخوانا | ۴۰۴ (K3-K5، F6) | ۴۰۴ | `enabled:false` | ۲۰۰ |

بازخورد با flag خاموش **پذیرفته نمی شود**؛ این رفتار عمدی و آزموده شده است. UI برای کسی که نه opt-in کرده نه دعوت شده، با flag خاموش هیچ کارتی نشان نمی دهد.

## ۴. تهدیدها و کنترل ها

| # | تهدید | کنترل فعلی | شاهد | ریسک باقی مانده |
|---|---|---|---|---|
| T1 | خواندن نتیجه با پارامتر تزریقی/آزاد | allowlist کلیدها، regex شناسه ایستگاه، تاریخ/ساعت اعتبارسنجی، `at=` رد، افق ۷ روز | B15/B16، تست های boundary | کم |
| T2 | اتلاف CPU/حافظه (DoS) | حداکثر ۲ کار هم زمان، ۶۰/دقیقه کل، ۱۰/دقیقه هر کلید، timeout ۵ ثانیه، بدون صف نامحدود | benchmark burst (فقط ۲۰۰/۴۲۹)، L1 | متوسط: مهاجم هماهنگ می تواند بودجه عمومی ۶۰/دقیقه را پر کند و برنامه ریز را برای دیگران ۴۲۹ کند (تابلو و بسفود بی اثر) |

| T6 | تزریق دستور/URL/نشت اطلاعات شخصی در متن | یادداشت ≤ ۲۰۰ نویسه و رد URL، markup، دستور، ایمیل، شماره، مختصات؛ هرگز اجرا یا fetch نمی شود؛ گزارش آفلاین یادداشت را چاپ نمی کند | B11، تست های feedback | متوسط: فیلتر نمی تواند ثابت کند اسم/اطلاعات شخصی نیست؛ UI هم هشدار می دهد |

## ۵. حریم خصوصی و داده

- ذخیره شده: خط، ایستگاه ها، جهت، نوع رخداد، زمان مشاهده، نتیجه کیفی، یادداشت کوتاه، شناسه گزارش تصادفی، نسخه مدل، زمان دریافت سرور. **نه** IP، مرورگر، حساب، GPS، تاریخچه سفر.
- شناسه گزارش را کاربر نمی بیند و در دستگاه ذخیره نمی شود؛ پس **بازخورد ناشناس بعداً به شخص نسبت داده یا فردی حذف نمی شود**؛ متن رضایت همین را می گوید.
- retention هدف ۳۰ روز است ولی **اجرای آن دستی** است (D3). تا زمان اجرای پاک سازی، داده ها می مانند؛ به همین دلیل UI عدد روز نمی دهد.
- export و گزارش تجمیعی یادداشت ها را چاپ نمی کنند؛ داده خام عمومی نشود. داده واقعی تاکنون وجود ندارد.

## ۶. تصمیم های لازم

| کد | موضوع | پیشنهاد |
|---|---|---|
| D1 | عمومی اختیاری یا محدود | عمومی اختیاری با برچسب Beta |
| D2 | محل آزمون گوشی | نخستین پنجره فعال سازی با `feedbackEnabled:false` |
| D3 | اجرای retention | پاک سازی دستی ماهانه؛ cron فقط با تصمیم جدا |

| D5 | دامنه ۳۶ فایل (hunk R0 + ماژول های بی اثر R1/R2a) | قبول |
| D6 | دو مرحله GO | بخش های ۱ تا ۶ با Beta خاموش، سپس تأیید جدا برای ۷ و ۸ |

## ۷. آنچه این مرحله ثابت نمی کند

امنیت در برابر مهاجم هماهنگ و بزرگ؛ رفتار واقعی روی ترافیک کاربران؛ صحت فیلتر متن برای همه زبان ها؛ رفتار در حافظه یا دیسک بسیار پرتر از حالت آزموده. این ها با پایش ۲۴ ساعت اول و پایش پس از گسترش دیده می شوند.
