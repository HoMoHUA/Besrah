# گزارش پایان R1 — Besrah Intelligence Core Foundation

**تاریخ:** ۲۰۲۶-۱۱-۰۲

**نتیجه:** Foundation مستقل پیاده سازی و اجرا شده؛ تست ها، typecheck، build و بازبینی مجدد اصلاحات موفق هستند.
**محدوده:** فقط کتابخانه داخلی، fixture مصنوعی، CLI محلی و مستندات. بدون Deployment و بدون ورود به R2.

## ۱. خلاصه اجرایی

R1 صرفاً مجموعه Interface یا پوشه نیست. تابع `evaluateDecision` ورودی نسخه دار را اعتبارسنجی می کند، مجوز تصمیم و محدودیت های سخت را بررسی می کند، گزینه های نامعتبر و نامعلوم را جدا می کند، گروه های هم ارز را با معیارهای اعلام شده مقایسه می کند، ترجیح صریح را اعمال می کند و نتیجه همراه با توضیح قابل ردیابی و حداکثر یک سؤال مؤثر می دهد.

- **۴۵۶ تست موفق، صفر شکست**؛ شامل **۱۵۱ تست جدید Intelligence Core** و **۳۰۵ تست موجود**.
- Core: **۲۲۹** تست؛ Mini App / data / n8n: **۱۹۸**؛ Release Inventory: **۱۲**؛ Python bus catalogue: **۱۷**.
- Typecheck، build، بررسی بازتولید داده اتوبوس و `git diff --check` موفق.
- هر ده سناریوی مصنوعی با CLI واقعی اجرا شدند؛ چهار ورودی نامعتبر CLI نیز با exit code برابر ۱ رد شدند.
- بازبینی مستقل ابتدا چهار ایراد پیدا کرد؛ اصلاح ها با تست رگرسیون بررسی شدند. بازبینی مجدد مستقل هیچ ایراد مسدود کننده امنیتی یا منطقی گزارش نکرد.
- درخت اصلی Dirty، index و HEAD آن حفظ شدند. هیچ فایل موجود در Production تغییر، حذف یا اضافه نشده است.

این نتیجه به معنی فعال شدن قابلیت جدید در محصول، تأیید داده زنده ارائه دهندگان یا ساخت مسیر یابی واقعی نیست.

### مسئولیت هر بخش

- `contracts.ts`: قرارداد نسخه ۱، پنج وضعیت Metric، Evidence، Candidate، Context، Constraint، Preference، Memory و نتیجه تصمیم؛ سقف های ورودی و واحدها.
- `validation.ts`: اعتبارسنجی واقعی runtime، فیلدهای مجاز، واحدها، نسخه، شناسه تکراری، زمان ISO معتبر، بازه ها، رضایت و شکل داده.
- `metrics.ts`: استخراج حدود قابل استفاده با ساعت صریح درخواست؛ رد داده منقضی و زمان مشاهده/بازیابی آینده.
- `constraints.ts`: نتیجه سه حالته محدودیت هزینه، زمان و دیگر Metric های پشتیبانی شده؛ امکان `requireKnown`.
- `compare.ts`: گروه بندی tuple بدون برخورد جداکننده، مقایسه پارتو و اولویت واژه نگاشتی صریح؛ داده ناقص جداگانه.
- `preferences.ts`: حل تقدم، رضایت، انقضا، provenance و تعارض ترجیحات؛ بدون یادگیری رفتاری.
- `memory.ts`: ساخت، اصلاح، حذف، پاک سازی و لغو ترجیح با snapshot مستقل، version و revision؛ بدون ذخیره ساز.
- `explain.ts`: اعداد و بازه های موجود با ارجاع به Metric و Evidence؛ بدون محاسبه صرفه جویی، midpoint یا ETA جدید.
- `questions.ts`: بررسی counterfactual محدود و حداکثر یک سؤال با دو پاسخ واقعاً مؤثر.
- `decision.ts`: orchestration خالص؛ ترتیب gate ها، مقایسه، ترجیح، برچسب و توضیح.
- `index.ts`: export کتابخانه؛ بدون ثبت route یا import در سرور محصول.

## ۴. رفتار قراردادها و تصمیم

### Evidence و Metric

حالت های `known`، `estimated`، `unknown`، `stale` و `not_applicable` مستقل هستند. سه حالت آخر مقدار قابل استفاده ندارند؛ مقدار مجهول به صفر تبدیل نمی شود. مقدار صفرِ معتبر با مدرک، واقعاً صفر باقی می ماند.

مقدار قابل استفاده Evidence با شناسه، منبع، نوع، نسخه داده و وضعیت live دارد؛ زمان مشاهده/بازیابی/اعتبار و روش استخراج در قرارداد پشتیبانی می شوند. Evidence مشتق شده باید `method` داشته باشد. Evidence از نوع fixture نمی تواند live باشد.

تخمین، فرض های صریح و مقدار و/یا بازه دارد. بازه هم پوشان با midpoint یا ضریب دلخواه به یک برنده قطعی تبدیل نمی شود. واحد هزینه تومان صحیح، زمان ثانیه، تعویض count و کیفیت مقیاس اعلام شده ۰ تا ۱۰۰ است؛ تبدیل امتیاز ارائه دهنده به این مقیاس اجرا نشده است.

انقضای `validUntil` و مشاهده/بازیابی آینده نسبت به `context.at` باعث غیرقابل استفاده شدن مقدار می شوند. ساعت جاری سیستم در تصمیم دخالت ندارد. نبود metadata اعتبار به معنی تأیید تازگی واقعی نیست؛ این مسئولیت Adapter آینده است.

### Context و محدودیت سخت

Context درخواست از Memory جدا است. `decisionPermission=denied` جلوی پیشنهاد را می گیرد. گزینه خلاف دامنه/وظیفه، ناموجود یا دارای محدودیت نقض شده از گزینه های معتبر جدا می شود. وضعیت موجودی نامعلوم یا محدودیت نامعلوم به بخش `undetermined` می رود.

نتیجه محدودیت فقط `satisfied`، `violated` یا `undetermined` است. بازه کاملاً داخل حد می تواند رعایت شده باشد؛ بازه کاملاً خارج، نقض شده؛ بازه عبوری از حد، نامعلوم. با `requireKnown` تخمین نیز برای اثبات رعایت کافی نیست.

### مقایسه و خروجی

- گروه ها برحسب domain/taskId/equivalenceKey مستقل هستند و با هم رتبه بندی نمی شوند.
- تمام objective های اعلام شده باید قابل ارزیابی باشند؛ مقایسه فقط روی اشتراک اتفاقی فیلدهای هر دو گزینه انجام نمی شود.
- پارتو، گزینه های دارای شواهد کامل را بررسی می کند؛ موارد ناقص در `incompleteIds` و نتیجه نامعلوم مشخص اند.
- در گروه ناقص، گزینه کامل می تواند به صورت موقت باقی بماند، اما برچسب قطعی پارتو، سریع ترین یا کم هزینه ترین نمی گیرد.
- دامنه همه برچسب ها فقط گزینه های هم ارز، واجد شرایط و ارائه شده است؛ ادعای بهترین گزینه کل شهر یا کل بازار نداریم.
- تعداد خروجی ثابت نیست. یک گزینه می تواند هم سریع ترین و هم کم هزینه ترین باشد، بدون ساخته شدن چند کارت تکراری.
- جهت min/max از objective می آید. وزن مخفی، امتیاز تجمیعی و تبدیل زمان به پول وجود ندارد.

### ترجیح و حافظه

ترجیح شامل domain/scope، provenance صریح یا inferred، تأیید کاربر، version، updatedAt، expiry و رضایت مستقل ذخیره/استفاده است. در R1 فقط ترجیح صریح و تأیید شده مصرف می شود؛ inferred در قرارداد حاضر است ولی در انتخاب دخالت ندارد.

تقدم: درخواست فعلی ← ترجیح محلی همان دامنه ← ترجیح محلی global. در هر سطح، زمان به روز رسانی جدیدتر ملاک است. تعارض هم زمان و هم سطح آشکار می شود؛ با ID، وزن مخفی یا ترجیح قدیمی تر حل نمی شود.

Override درخواست با رضایت استفاده و بدون رضایت ذخیره قابل اعمال است، اما خودکار ذخیره نمی شود. حافظه محلی فقط با رضایت ذخیره و scope دستگاه قابل upsert است؛ نسخه باید دقیقاً یک واحد افزایش یابد، زمان عقب نرود و سقف رعایت شود. عملیات immutable هستند. `revokePreference` داده ترجیح را حذف می کند.

کاربر ناشناس بدون Memory کاملاً پشتیبانی می شود. این مرحله snapshot سریال شدنی و رفتار قطعی حافظه را فراهم می کند، نه localStorage متصل به UI یا DB سروری.

## ۵. اجرای واقعی روی fixture ها

**تمام اعداد این بخش مصنوعی و صرفاً داده تست هستند؛ قیمت، تعرفه یا زمان واقعی محصول نیستند.** هر ده سناریو بیرون از public assets قرار دارند و Evidence آن ها `fixture` و `live:false` است.

```sh
cd /root/projects/besrah-r1
npm --prefix packages/core run build
node scripts/demo-intelligence.mjs
node scripts/demo-intelligence.mjs --scenario anonymous-question
node scripts/demo-intelligence.mjs --scenario request-override
```

در سناریوی ناشناس:

- `fixture:economical`: هزینه ۱۰۰ تومان، مدت ۱۲۰۰ ثانیه.
- `fixture:quick`: هزینه ۴۰۰ تومان، مدت ۶۰۰ ثانیه.
- نتیجه: هر دو گزینه باقی ماندند؛ اولی `lowest_cost` و دومی `fastest`، هر دو `pareto_option` در همین مجموعه مشخص.
- یک سؤال: «کدام ترتیب اولویت را ترجیح می دهید؟»
- پاسخ هزینه سپس زمان، گزینه economical را انتخاب می کند؛ پاسخ زمان سپس هزینه، گزینه quick را. این تفاوت روی گزینه های موجود محاسبه شده است.

در `local-preference`، انتخاب `fixture:economical` بود. در `request-override`، ترجیح موقت زمان مقدم شد و انتخاب به `fixture:quick` تغییر کرد؛ ترجیح ذخیره شده با دلیل `overridden` کنار رفت و Memory ورودی تغییر نکرد.

نمونه claim واقعی خروجی:

```json
{
  "code": "metric:totalCostToman",
  "text": "هزینه: 400 تومان.",
  "refs": [{
    "candidateId": "fixture:quick",
    "metric": "totalCostToman",
    "evidenceIds": ["fixture:quote-v1"]
  }]
}
```

دیگر نتایج مشاهده شده:

- `hard-gates`: گزینه بالای بودجه حذف؛ قیمت نامعلوم جدا؛ status برابر `partial`.
- `multiple-labels`: تنها `fixture:best` با برچسب های پارتو، کم هزینه ترین و سریع ترین؛ گزینه مغلوب جدا در گروه.
- `no-feasible`: صفر گزینه و `no_feasible_option`.
- `stale-evidence`: صفر گزینه و `insufficient_data`؛ نه قیمت صفر و نه داده سالم.
- `non-equivalent`: دو گروه مستقل، بدون مقایسه بین آن ها و بدون سؤال مشترک.
- `preference-conflict`: دو ترجیح متعارض ثبت شدند؛ انتخاب دلخواه انجام نشد.
- `overlapping-estimates`: بازه ها حفظ شدند؛ میانگین ساختگی تولید نشد.

## ۶. تست ها و پذیرش

اجرای نهایی همه گروه ها سری بود؛ Vitest با یک worker و بدون file parallelism و Node با concurrency برابر یک اجرا شد.

```sh
npm --prefix packages/core run typecheck
npm --prefix packages/core test -- --maxWorkers=1 --no-file-parallelism
node --test --test-concurrency=1 apps/miniapp/*.test.mjs tests/data/*.test.mjs tests/n8n/*.test.mjs
python3 -W error::ResourceWarning -m unittest discover -s tests/release -v
python3 -W error::ResourceWarning -m unittest discover -s tests/data -p 'test_*.py' -v
python3 scripts/build_bus_app_data.py --check
npm --prefix packages/core run build
```

همه دستورها exit code صفر داشتند. اجرای build و typecheck جداگانه تأیید شده، نه این که از پاس شدن تست استنباط شود.

### پوشش معیارهای درخواست

- مجهول/منقضی: Metrics، Constraints، Explain و سناریوی stale.
- تخمین و هم پوشانی بازه: Constraints، Compare، Explain و fixture مربوط.
- هزینه/زمان سخت: Constraints و Decision؛ ترجیح نمی تواند gate را دور بزند.
- ترجیح متعارض، override فعلی و تقدم دامنه: Preferences، Memory و Decision.
- غیرهم ارزی و پارتو: Compare و Decision؛ بدون رتبه بندی بین گروه ها.
- صفر گزینه و چند عنوان یک گزینه: Decision و fixture های no-feasible/multiple-labels.
- provenance، تأیید، رضایت، انقضا، حذف و version: Preferences و Memory.
- سؤال مؤثر/غیرمؤثر: Questions؛ مقایسه مجموعه ID انتخاب شده بعد از دو پاسخ واقعی، نه صرفاً تغییر ترتیب نمایش.
- توضیح مستند: Explain و Decision؛ اعداد دقیق/بازه های موجود و evidence ID قابل ردیابی.
- نبود side effect: جلوگیری از استفاده از Date.now، randomness، fetch و localStorage در تست ورودی مستقل؛ import های کتابخانه نیز داخلی هستند.
- پردازش محدود: سقف ورودی، رد overflow، شمارنده و نمونه های ظرفیت.

تست مرورگر یا صحت Provider زنده، تضمین همه رفتارهای Production و آزمون بار سراسری در R1 ادعا نشده است؛ این مرحله به API/UI محصول متصل نیست.

## ۷. بازبینی و اصلاح های رگرسیون

چهار یافته مسدود کننده بازبینی نخست:

۱. خواندن discriminator قبل از رد getter می توانست side effect اجرا کند؛ اکنون descriptor قبل از خواندن state بررسی می شود.
۲. آرایه sparse از forEach عبور می کرد؛ اکنون هر index باید own data property باشد.
۳. Metric غیر enumerable می توانست محدودیت عدد صحیح تومان و تعداد Evidence را دور بزند؛ فیلد hidden/symbol در object و array رد می شود.
۴. گزینه ناقص رقیب می توانست با وجود شواهد نامعلوم، توضیح قطعی پارتو برای گزینه دیگر ایجاد کند؛ برچسب های قطعی گروه ناقص حذف شدند، نه خود گزینه موقت یا داده نامعلوم.

برای این موارد تست بازتولید نوشته شد و شکست پیش از اصلاح مشاهده شد. در بازبینی مجدد مستقل، هر چهار اصلاح و سقف سؤال و cache محلی bounds بررسی و بدون یافته مسدود کننده تأیید شدند. این بازبینی مجدد static بود؛ نتایج runtime این گزارش از اجرای مستقل عامل اصلی آمده اند.

یک نکته غیرمسدود کننده نیز مستند شد: قطعیت برای ورودی مرتب یکسان برقرار است؛ ترتیب diagnostics ترجیحات نادیده گرفته شده، ترتیب ورودی را حفظ می کند و تضمین canonical serialization برای آرایه ترجیح reorder شده نداریم.

## ۸. پردازش و حافظه اندازه گیری شده

سقف ها: ۱۲۸ گزینه، ۶ objective، ۱۶ محدودیت، ۶۴ ترجیح حافظه و ۶۴ ترجیح درخواست، ۸ Evidence برای هر Metric، متن و فرض های محدود.

مقایسه پارتو در بدترین اندازه گروه، مربعی ولی محدود است. سؤال به جای تمام ۷۲۰ جایگشت، حداکثر شش ترتیب promotion را امتحان می کند. برای برچسب هر گزینه، شواهد همه همتایان دوباره parse نمی شوند؛ bounds فقط در همان درخواست cache می شود. تستی که ۴۳۵۲ فراخوانی تکراری را بازتولید می کرد، پس از اصلاح زیر سقف تعیین شده قرار گرفت.

محیط واقعی اجرا: Node `v22.23.4`، npm `10.9.9`.

### نمونه ۱۲۸ گزینه / دو معیار / ۱۰۰ تکرار

- p50: **15.43 ms**؛ p95: **23.09 ms**؛ بیشینه: **28.40 ms**.
- ۸۱۲۸ جفت در pass اصلی پارتو.
- RSS فرایند پس از نمونه: **95.02 MiB**؛ heap used پس از نمونه: **19.26 MiB**.

### نمونه ظرفیت فشرده / هر کدام ۱۰ تکرار

- ۱۲۸ گزینه هم ارز مساوی، شش معیار، شانزده محدودیت و هشت Evidence برای هر Metric: بیشینه **272.51 ms**؛ RSS نمونه **99.32 MiB**.
- همان ظرفیت همراه با ۶۴ ترجیح حافظه و ۶۴ ترجیح درخواست: بیشینه **198.45 ms**؛ RSS نمونه **114.57 MiB**.
- هر مورد: ۲۰۴۸ بررسی محدودیت و ۸۱۲۸ جفت در pass اصلی مقایسه.

این اعداد نمونه محلی مصنوعی هستند؛ نه SLO، نه اندازه دقیق حافظه اختصاص یافته به کتابخانه، نه تضمین سقف V8 و نه latency ارائه دهنده. RSS شامل runtime است و GC روی heap اثر می گذارد. `pairComparisons` فقط pass اصلی پارتو را می شمارد، نه تمام مقایسه های سؤال/ترجیح/برچسب.

در R2 باید قبل از ورود این کتابخانه به مسیر HTTP، سقف واقعی candidate ها، latency budget و رفتار event loop برای ورودی هدف تعیین و اندازه گیری شود؛ نمونه ظرفیت فشرده، تضمین پاسخ آنی نیست.

## ۹. تصمیم ها و Trade-off ها

- Modular Monolith و TypeScript موجود حفظ شد؛ سرویس، DB، dependency و runtime مدل جدید ساخته نشد.
- ورودی مبهم fail-closed است؛ حدس واحد، مقدار، رضایت یا نسخه به جای caller انجام نمی شود.
- `evaluateDecision(unknown)` مرز اعتبارسنجی کامل است؛ helper های سطح پایین برای داده typed/اعتبارسنجی شده هستند، نه جایگزین این ورودی اصلی.
- هم ارز بودن واقعی و هویت گزینه را Adapter آینده باید اثبات کند؛ رشته equivalenceKey به تنهایی حقیقت تجاری را کشف نمی کند.
- اولویت صریح واژه نگاشتی انتخاب شد، نه وزن دلخواه. این نسخه مطلوبیت پیوسته، تبدیل پول به زمان یا ریسک احتمالاتی را مدل نمی کند.
- بازه های یکسان به عنوان نمایش یکسان عدم قطعیت برابر در نظر گرفته می شوند؛ این سیاست، اثبات برابری مقدار واقعی پنهان یا مدل همبستگی عدم قطعیت نیست.
- جست و جوی سؤال عمداً کامل نیست؛ ممکن است trade-off موجود در جایگشت های امتحان نشده را کشف نکند، اما سؤال بی اثر تولید نمی کند.
- حافظه snapshot محلی و صریح است؛ هیچ مشاهده رفتاری، auth، sync، retention policy سروری یا ادعای ذخیره امن دستگاه اضافه نشده است.
- `decisionPermission` سیاست ورودی caller برای پیشنهاد است، نه توکن هویت یا اجازه پرداخت/سفارش خودکار.
- داده واقعی جدید وارد محصول نشد. تست مصنوعی، صحت منبع واقعی یا freshness ارائه دهنده را ثابت نمی کند.

## ۱۰. قابلیت هایی که هنوز وجود ندارند

- Adapter واقعی Transit/Food/Shopping و اتصال هسته به محصول؛
- مسیر یابی A→B چندوجهی، walking/entrance/transfer کامل یا زمان بندی اتوبوس کل شهر؛
- تأیید قیمت، موجودی، هزینه نهایی سفارش، کرایه یا وضعیت لحظه ای ارائه دهندگان؛
- UI حافظه، ذخیره ساز دستگاه متصل، حافظه سروری، حساب کاربری یا همگام سازی؛
- یادگیری رفتاری و مصرف ترجیحات inferred؛
- LLM، درک درخواست زبان طبیعی یا تولید متن آزاد مدل؛
- Automation، رزرو، خرید، پرداخت یا مجوز محدود اجرای واقعی؛
- API عمومی جدید، تغییر HM7 یا انتشار.

وجود Foundation به معنی وجود این قابلیت ها نیست.

## ۱۱. پیشنهاد R2، بدون اجرا

جزئیات در `R2-TRANSIT-ADAPTER-PROPOSAL.md` آمده است. نخستین واحد پیشنهادی، Adapter خواندنی سفر ایستگاه به ایستگاه مترو بر پایه `dayTrains` و `line2DayTrains` و epoch های `arrive/depart` موجود است.

محدوده سفر، شناسه ایستگاه/خط، روز خدمت، شناسه سفر دارای تاریخ و هم ارزی وظیفه باید صریح باشند. انتظار و مدت سفر از توقف واقعی مدل مشتق شوند، نه عدد گرد شده `/next` یا هندسه ردیاب. زمان های برنامه حرکت همچنان تخمینی اند. کرایه نامعلوم نباید صفر شود و وارد ادعای اقتصادی واقعی شود.

ابتدا همان خط و بدون تعویض/پیاده روی خیابانی؛ سپس فقط با شواهد و مجوز مرحله جداگانه، کریدور دارای entrance، walking، transfer و fare. داده topology اتوبوس جای schedule قرار نگیرد. تست های موتور موجود و API ها حفظ شوند.

**در R1 هیچ فایل Adapter واقعی یا اتصال محصول ساخته نشده است.**
