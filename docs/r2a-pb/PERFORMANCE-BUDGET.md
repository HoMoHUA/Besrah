# بودجه عملکرد R2a-PB — پیش از benchmark

این بودجه ها پیش از اجرای benchmark این مرحله ثبت شده اند. عبور از بودجه با افزایش محدودیت حافظه یا شل کردن assertion مجاز نیست؛ شکست باید رفع یا به عنوان blocker گزارش شود. اعداد R2a قبلی، نتیجه PB نیستند.

## محیط و کنترل بار

- فقط candidate و loopback؛ هیچ درخواست بار به Production یا provider بیرونی فرستاده نمی شود.
- cgroup واقعی: `MemoryMax=192M`، `MemorySwapMax=0` و `TasksMax=64`.
- مسیر مدل همان R1/R2a واقعی، با حداکثر دو کار هم زمان مجموع برنامه ریز و بازخورد؛ حداکثر یک ثبت بازخورد هم زمان. صف درخواست HTTP نداریم؛ فشار اضافه `429` می گیرد.
- beta و feedback پیش فرض خاموش؛ در مرحله اول حداکثر ۶۰ خواندن در دقیقه، ۱۰ خواندن برای هر کلید موقت IP در دقیقه؛ ۳۰ تلاش بازخورد در دقیقه و ۱۰ تلاش برای هر کلید موقت در ساعت. IP یا hash آن روی دیسک ثبت نمی شود.
- پنجره مدل ۱۲۰ دقیقه است، نه ۶۰ دقیقه: سفر کامل خط ۱ به فرودگاه ممکن است بیش از یک ساعت باشد و موتور R2a زمان رسیدن را نیز در افق جستجو محدود می کند. این بودجه برای همان افق ۱۲۰ دقیقه تعیین شده است.
- حداکثر ۵ گزینه نمایشی، ۱۲ کاندید موتور و ۷ روز آینده. حذف گزینه برای سقف نمایش، `partial` و `coverage.truncated=true` می شود؛ گزینه با کمترین زمان رسیدن از میان کاندیدهای بررسی شده حفظ می شود.
- timeout پاسخ ۵ ثانیه؛ timeout ظرفیت موتور در حال کار را آزاد نمی کند. ظرفیت فقط پس از پایان واقعی کار آزاد می شود.
- ذخیره JSONL با fsync، quota کل ۸ MiB، حداکثر ۲۰۰۰ گزارش در روز و retention تعریف شده ۳۰ روز. داده تست و بازخورد واقعی در پوشه های جدا قرار می گیرند.

## Gate های کمی

- API برنامه ریز warm، بار سری: `p95 <= 80 ms`؛ cold: `<= 250 ms`.
- برنامه ریز با concurrency برابر ۲: `p95 <= 150 ms`.
- فشار cache با جابه جایی خط و تاریخ، concurrency حداکثر ۲: `p95 <= 200 ms`.
- API قبلی در بار ترکیبی: `p95 <= 50 ms` و افزایش نسبت به baseline همان اجرای مستقل `<= 30 ms`؛ نسبت و اختلاف هر دو گزارش می شوند.
- ثبت بازخورد پذیرفته شده و durable در بار گرم: `p95 <= 50 ms`؛ بازگشایی store نزدیک quota جداگانه اندازه گیری می شود، سقف `500 ms`.
- event loop delay: `p95 <= 30 ms` و `max <= 150 ms` در بار کنترل شده؛ نمونه cold و فشار cache جدا ثبت می شود.
- RSS اوج کل process آزمون `<= 170 MiB`، cgroup memory peak `<= 184 MiB`، سقف واقعی ۱۹۲ MiB و swap صفر؛ OOM و OOM kill صفر.
- در بار مجاز، پاسخ برنامه ریز ۲۰۰ و API قبلی بدون خطا؛ در burst بیش از ظرفیت فقط ۲۰۰ یا ۴۲۹ مجاز است، نه صف نامحدود یا ۵۰۰.
- خطای مدل، timeout و خطای فایل/فساد store باید پاسخ کنترل شده بدهند. API قبلی باید کار کند و پس از رفع خطای آزمایشی، مسیر مربوط دوباره قابل استفاده باشد. خطای ذخیره نباید ACK موفق ساختگی بدهد.

## ثبت و بازتولید

دستور اجرا، نسخه Node، نسخه candidate، timestamp، تعداد نمونه هر فاز، p50/p95/max، وضعیت HTTP، event loop، RSS و رویدادهای cgroup در خروجی JSON و لاگ خصوصی checkpoint ثبت می شوند. benchmark همان cgroup را از `/proc/self/cgroup` احراز می کند. اندازه گیری client در process آزمون نیز لحاظ می شود و جای load test چند کاربر واقعی را نمی گیرد. تغییر بعدی بودجه فقط با تصمیم تازه مالک مجاز است، نه برای سبز کردن نتیجه فعلی.
