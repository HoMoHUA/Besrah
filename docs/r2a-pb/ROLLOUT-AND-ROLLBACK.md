# طرح انتشار و بازگشت R2a-PB

> **به روز رسانی پیش پرواز (R2a-PB preflight):** دستورهای اجرایی، ترتیب مراحل، مسیر فایل کنترل (`/etc/besrah-journey/control.json`؛ `/etc/besrah` برای DynamicUser ناخواناست)، `StateDirectory`، allowlist دقیق فایل ها و rollback آزموده در `docs/r2apb/RELEASE-RUNBOOK.md` قرار دارند و بر این سند مقدم اند. در این سند عبارت «rehearsal فعلی ... UID/sandbox عمدا برای بعد باقی می ماند» دیگر صادق نیست: sandbox معادل و Nginx جداگانه با گواهی واقعی آزموده شدند (`docs/r2apb/PREDEPLOY-GO-NOGO-REPORT.md`). مواردی که فقط در Production واقعی قابل تأیید هستند همچنان در پنجره استقرار می مانند.


**این سند برنامه انتشار است، نه مجوز یا سابقه استقرار.** Production، Nginx، بات و بسفود این مرحله تغییر نمی کنند. نتیجه Gate در گزارش آمادگی تعیین می شود؛ `BLOCKED` با GO معمولی به PASS تبدیل نمی شود. ابتدا blocker فنی باید رفع و دوباره آزموده شود، سپس GO جداگانه مالک لازم است.

## بسته و پیش نیاز

- شاخه مستقل `feature/r2a-production-beta` بر مبنای D2 مصوب؛ موتورهای قبلی و داده خام بدون تغییر.
- Node فعلی آزمون شده 22.23.4؛ dependency جدید، DB سنگین، صف یا LLM اضافه نشده است. dependency lock مرجع همان package-lock است.
- اجرای پیش نمایش از ریشه candidate: `npm --prefix packages/core run build` سپس `node scripts/preview-journey-beta.mjs`. فقط `127.0.0.1:18864`؛ پوشه بازخورد خصوصی آزمون در TMPDIR چاپ می شود. این داده ها شاهد میدانی نیستند. اجرای پیش نمایش نرخ ها را فقط برای QA بالا می برد، ولی concurrency همان دو است؛ این تنظیمات نباید به Production منتقل شوند.
- تست کامل سری، typecheck/build، بازتولید bus و inventory معتبر لازم اند. manifest تفاوت candidate/deployed را ثبت می کند، نه امضا یا اثبات کامل build-to-source.
- سقف سرویس `MemoryMax=192M` و swap فعلی افزایش پیدا نمی کند. بودجه های از پیش ثبت شده در PERFORMANCE-BUDGET.md بدون کاهش کیفیت تست ملاک اند.

## مراحل پس از رفع blocker و GO مالک

### ۰. snapshot و candidate خاموش

1. پیش از تغییر، snapshot خصوصی و قابل بازیابی از تمام release فعلی، dist، Mini App، داده های allowlist، فایل های واحد سرویس و fragment فعلی Nginx گرفته شود. secret در Git یا گزارش قرار نگیرد. export بازخورد فقط در snapshot خصوصی بدون writer فعال.
2. manifest deployed با hash فایل های واقعی، وضعیت service/PID و smoke قدیمی ثبت شود؛ checkout Git به تنهایی backup نیست. candidate تمیز، مجزا و reproducible ساخته و inventory آن دوباره validate شود.
3. candidate جدید ابتدا با بتای خاموش در مسیر release مجزا آزمایش شود. مسیر بازخورد خارج release و خارج web root، پوشه0700 و فایل0600 تحت UID واقعی سرویس تعیین شود. سازگاری StateDirectory، مجوز نوشتن sandbox و lock با همان UID در پنجره انتشار بررسی شود؛ اجرای فعلی preview تحت root معادل این آزمون نیست.
4. تغییر نام release یا symlink فقط پس از smoke و طبق سازوکار استقرار پروژه انجام شود؛ این مرحله دستور کپی کور به `/srv/besrah` ندارد. هر restart لازم فقط در اجرای مجاز بعدی و پس از backup انجام می شود.

### ۱. ورود داوطلبانه واقعی

- feature flag اصلی پیش فرض خاموش؛ پس از smoke نسخه خاموش و تایید نسخه مستقر، `BESRAH_JOURNEY_BETA=on` همراه switch file معتبر انتخاب شود.
- control اولیه: `{"schemaVersion":1,"enabled":true,"feedbackEnabled":true,"rolloutPercent":0}`. مالک فایل را با مجوز مناسب و atomic rename جایگزین کند. share صفر یعنی عدم ترویج انتخابی، نه منع ورود داوطلبانه؛ ورودی اختیاری صفحه مترو و لینک `?beta=1` به کاربران واقعی اجازه ورود می دهند. تایید حساب یا allowlist ثابت ادعا نمی شود.
- همه صفحه ها برچسب آزمایشی و هشدار مدل/تقویم دارند. استفاده بدون بازخورد، خروج از بتا و حذف انتخاب opt-in محلی ممکن است. تاریخچه سفر ذخیره نمی شود.
- نرخ های Production همان default اند:۶۰ خواندن در دقیقه کل،۱۰ برای هر کلید موقت در دقیقه؛۳۰ تلاش ثبت در دقیقه کل،۱۰ برای هر کلید در ساعت؛ حداکثر دو کار و یک ثبت هم زمان، بدون صف نامحدود. تکرار یا فشار اضافه باید429 بگیرد. هدف انتشار اول جمع آوری کوچک و داوطلبانه است، نه تضمین ظرفیت عمومی شهر.
- تنها مجوز POST جدید، fragment دقیق `nginx-feedback-route.conf` داخل server بسراه است. prefix عمومی `/api/` و `/` همان GET/HEAD می مانند. Origin/header/schema و size/rate هم در core برقرار اند؛ Nginx جای آن ها را نمی گیرد. fragment فقط در یک Nginx مستقل loopback آزموده شده و روی Production نصب نشده است.

### ۲. smoke انتشار

- نسخه/manifest deployed با candidate تاییدشده تطبیق داده شود؛ `/health`، registry، تابلو هر دو خط، tracker، bus و باز شدن catalogue بسفود بررسی شوند. provider خارجی بسفود بدون آزمون جداگانه، سالم فرض نشود.
- feature خاموش: journey404 و API قدیمی200؛ سپس روشن: دو خط/دو جهت، غدیر/فرودگاه و هشدار غیرجمعه؛ strict بدون تقویم معتبر گزینه ساختگی ندارد.
- روی Origin واقعی، بدون consent هیچ POST صادر نشود؛ گزارش آزمایشی برچسب خورده در پوشه آزمون جدا201 و retry همان ID برابرduplicate؛ بازخوانی durable و مجوز فایل بررسی شود. آزمون smoke نباید وارد مجموعه مشاهده واقعی شود.
- POST به مسیرهای دیگر403، GET مسیر feedback403، Origin بیگانه403، بدنه بزرگ413، malformed400، نرخ اضافه429. هیچ token یا بدنه در access/error log ثبت نشود.
- خاموشی feedback تنها، سپس خاموشی کل beta از switch بدون restart آزموده شود؛ تابلو و بسفود مستقل بمانند. توقف flag، کار از قبل پذیرفته شده را به زور لغو نمی کند، ولی پذیرش تازه را قطع می کند.
- آزمون واقعی Telegram WebView روی گوشی پیش از عمومی کردن beta انجام شود؛ Chromium desktop حتی با emulation جای آن نیست. RTL، صفحه کلید native، time input، consent و ارسال در اینترنت ضعیف جزو این smoke هستند.

### ۳. مشاهده و گسترش کنترل شده

- در۲۴ساعت اول، نمونه برداری سبک loopback از latency/status با concurrency محدود؛ هیچ IP، payload یا query خصوصی در گزارش پایش نماند. baseline API قدیمی و p50/p95، خطای5xx،429، event loop، RSS/cgroup و شمار OOM پایش شوند. probe، ظرفیت تست و دسترسی به داده واقعی را مخلوط نکند.
- هر عبور از بودجه ثابت، OOM، رشد حافظه، خطای durable، خرابی store، نشت داده یا رگرسیون تابلو سبب توقف گسترش و خاموشی بتا می شود. 429 در burst کنترل پذیر است، ولی اشباع پیوسته شاخص توقف گسترش است، نه مجوز زیاد کردن منابع.
- یک snapshot خصوصی بدون نویسنده فعال برای گزارش `beta_feedback_report.py report --strict` تهیه شود: شمار معتبر/نامعتبر، نسخه ها، پوشش خط/جهت/روز/ساعت، نمونه های ناشناس و صف QC؛ بدون گزارش کافی «دقت هنوز اندازه گیری نشده است».
- share پس از مرور مالک به۱۰، سپس۲۵ و حداکثر۱۰۰ افزایش یابد؛ هر مرحله حداقل یک بازه مشاهده و بررسی خطا/بازخورد دارد. این درصد فقط ترویج محلی UI با bucket تصادفی غیرشخصی است، نه تخمین درصد دقیق کاربران یا امنیت API. محدودیت کل نرخ ثابت می ماند؛ رشد فراتر از ظرفیت به کار مستقل نیاز دارد.
- گزارش تکی، feedback کیفی یا تطبیق نام قطار هیچ جدول یا وضعیت estimated را عوض نمی کند. ingest→QC→شاهد مستقل→شاخه کالیبراسیون→held-out→تصویب مالک→نسخه جدید؛ R2b همچنان بسته است.

## خاموشی و rollback

1. سریع ترین قطع: atomic replace switch با `enabled:false`؛ اگر switch نامعتبر یا حذف شود نیز fail-closed است. برای توقف فقط ثبت، `feedbackEnabled:false`. مسیرهای قدیمی به flag وابسته نیستند.
2. در خطای امنیتی، exception دقیق POST از نسخه تاییدشده قبلی Nginx بازگردانده و syntax/reload فقط در پنجره مجاز عملیات انجام شود. به هیچ وجه POST عمومی باز نشود.
3. اگر لازم شد release قبلی دقیق با manifest و snapshot برگردد؛ dist و asset مخلوط از دو نسخه تحویل نشود. پس از بازگشت hash، smoke قدیمی و وضعیت حافظه دوباره تایید شود.
4. بازخورد خصوصی خارج release حفظ و writer بسته شود؛ rollback مدل، حذف بازخورد یا پاک کردن شواهد خطا نیست. stale lock هرگز خودکار برداشته نشود. backup ها نیز retention و حذف خصوصی مستقل دارند.
5. rehearsal فعلی در محیط مستقل، بازیابی bundle/فایل ها، flag kill و route policy را آزموده است؛ restart، UID/sandbox واقعی، TLS/Origin نهایی و گوشی واقعی عمدا برای اجرای بعد از مجوز باقی می مانند. این تفاوت ها در Gate نهایی پنهان نمی شوند.
