# عملیات آفلاین بازخورد بتا

این ابزار داخلی است؛ HTTP، پایگاه داده، cron، LLM، تغییر جدول قطار و استقرار ندارد. ادعای ناشناس همیشه `anonymous_unverified` می ماند. تایید QC هویت فرستنده یا اصالت شواهد را اثبات نمی کند. بدون مشاهده مستقل کافی، دقت هنوز اندازه گیری نشده است؛ ورودی خالی به `accuracy.status=unavailable` و `n=0` می رسد.

## ورودی و حریم خصوصی

- مرجع رکورد خام: `packages/core/src/journey-beta/feedback.ts` و قرارداد `API-CONTRACT.md`. فایل های `feedback-YYYY-MM.jsonl` دارای `schema:1` هستند. نسخه قدیمی بدون provenance خوانده می شود؛ نسخه جدید باید هر چهار فیلد `sourceId`, `reportedAt`, `consent`, `provenance` را با مقدارهای دقیق ذخیره ساز داشته باشد. رضایت یا provenance برای رکورد قدیمی ساخته نمی شود.
- `sourceId` فعلی دقیقا `anonymous_feedback:<reportId>` است؛ شناسه شخص یا شاهد مستقل نیست. `reportedAt` همان زمان دریافت سرور است، نه ساعت مشاهده یا ساعت مستقل دستگاه کاربر.
- مرجع سازگاری این ممیزی کد فعلی ذخیره ساز است: در مشاهده ذخیره شده، `precision` همچنان `minute/approximate` است و فیلد افزوده و اختیاری `timePrecision` با مقدار `minute/second/unknown` بدون حذف یا ارتقای اعتماد خوانده می شود. رکورد قدیمی بدون این فیلد هم پذیرفته است. در ورودی فعلی Node، نبود precision به `approximate` و نبود هر دو فیلد به timePrecision برابر `unknown` تبدیل می شود؛ precision قدیمی minute، در نبود timePrecision، مقدار minute تولید می کند. این ها همه ادعای فرستنده اند، نه اندازه گیری مستقل.
- رد شدن هنگام دریافت فقط در `rejections-YYYY-MM.json` به تفکیک reason code مجاز شمارش می شود. محتوای درخواست ردشده در گزارش نیست. رد شدن هنگام QC جداگانه شمارش و از تحلیل کنار گذاشته می شود.
- reason code های فعلی دقیقا `malformed_request`, `forbidden_origin`, `rate_limited`, `invalid_payload`, `storage_full`, `storage_unavailable`, `busy`, `model_unavailable`, `feedback_timeout`, `disabled`, `other` هستند. ساختار شمارنده دقیقا `{month, counts, updatedAt}`، زمان UTC با سه رقم میلی ثانیه و Z، و مقدار هر شمارنده عدد صحیح مثبت و امن JavaScript است. کلید ناشناخته، زمان نامعتبر یا صفر معتبر نیست.
- `quota.json` داده بازخورد یا شمار رد شدن نیست: دقیقا `{schema:1, semantics:"deleted_intake_offsets", counts:{"YYYY-MM-DD":positiveInteger}}` است. شمار intake روز UTC برابر تعداد سطرهای خام باقی مانده به اضافه offset های حذف قبلی است؛ این فایل هرگز با شمار رکوردهای فعلی جایگزین یا صفر نمی شود. CLI حداکثر ۳۶۶ روز، ۱۶ KiB، عدد صحیح امن و نبود overflow با رکوردهای باقی مانده را کنترل می کند؛ خرابی آن exit ۲ است، نه نادیده گرفتن سهمیه.
- متن `note`، `basis`، شناسه بازبین، زمان دقیق مشاهده و مسیر فرد در export نیست. گزارش داخلی JSON/Markdown می تواند شناسه گزارش در صف QC داشته باشد؛ آن را عمومی نکنید. export فقط تجمیع کمینه JSON یا جدول پوشش CSV است؛ حتی سلول تک نمونه هم فقط مصرف داخلی دارد.
- SHA-256 اثر انگشت محتوا است، نه امضا یا احراز اصالت. ابزار همواره `signature_state=not_provided` اعلام می کند؛ تایید امضای بیرونی پیاده نشده است.
- سقف ها: فایل و مجموع ورودی شناخته شده هر کدام ۶۴ MiB، هر رکورد ۸ KiB، حداکثر ۵۰٬۰۰۰ خط بازخورد و ۵۰٬۰۰۰ خط بازبینی، حداکثر ۱۲۰ ورودی پوشه. عبور از سقف کل، خطای توقف است؛ تحلیل ناقص به جای گزارش کامل ارائه نمی شود. symlink و فایل غیرعادی خوانده نمی شوند. بدنه API همچنان سقف مستقل ۴۰۹۶ بایت دارد؛ این CLI بدنه HTTP دریافت نمی کند.

## گزارش و export بازتولیدپذیر

روی snapshot خصوصی و بدون نویسنده فعال اجرا کنید. این فرمان ها سرویس را متوقف نمی کنند و اجازه تغییر Production نمی دهند. `$SNAPSHOT` باید مسیر یک کپی آفلاین باشد و `$OUTPUT` پوشه خصوصی بیرون آن.

وجود هر نوع `.feedback.lock`، حتی خالی، symlink یا ظاهرا متعلق به PID مرده، باعث رد شدن تمام فرمان ها می شود. سن lock یا نبود PID مجوز تصاحب آن نیست. برای lock باقی مانده از crash، ابتدا مالک باید توقف همه writer ها و درستی فایل ها و نبود فایل موقت یا سطر نیمه نوشته را بررسی کند؛ حذف lock عملیات جداگانه مالک است و CLI آن را خودکار انجام نمی دهد. report/export فقط وجود lock را پیش و پس از خواندن کنترل می کنند و قفل خواندن نمی گیرند؛ بنابراین همچنان به کپی واقعا آفلاین نیاز دارند و جای پروتکل snapshot گرفتن از writer فعال نیستند.

```bash
python -B scripts/beta_feedback_report.py report --dir "$SNAPSHOT" --strict \
  --json "$OUTPUT/feedback.json" --md "$OUTPUT/feedback.md"
python -B scripts/beta_feedback_report.py export --dir "$SNAPSHOT" \
  --format json --out "$OUTPUT/aggregate.json"
python -B scripts/beta_feedback_report.py export --dir "$SNAPSHOT" \
  --format csv --out "$OUTPUT/coverage.csv"
```

`reviews.jsonl` داخل snapshot خودکار خوانده می شود؛ مسیر مستقل با `--reviews FILE` ممکن است. زمان تولید پیش فرض `null` است؛ فقط `--generated-at ISO_WITH_OFFSET` آن را ثابت می کند. ترتیب خروجی ثابت، مجوز فایل 0600 و انتشار export کامل و بدون overwrite است. CSV در برابر فرمول با پیشوند نقل قول محافظت می شود. exit code: صفر موفق، ۲ ورودی نامعتبر یا عملیات ردشده، ۳ وجود مشکل صحت داده با `report --strict`. export تعداد مشکل های صحت داده را در خلاصه اعلام می کند؛ برای QC ابتدا گزارش strict را بررسی کنید.

پوشش و کیفیت نمونه با `line`, `direction`, `serviceDate`, ساعت تهران، `event`, وضعیت بازبینی، `modelVersion` و split تجمیع می شوند. `eligibleIndependentObservations` تعداد شاهد قابل تطبیق هر سلول است؛ معیار خطا برای هر سلول هم فقط با حداقل ۳۰ نمونه held-out چاپ می شود. خرابی ورودی، فایل ناخوانا، شمارنده رد شدن نامعتبر یا بازبینی نامعتبر، `statistics.integrity_gate=blocked` ایجاد می کند و انتشار همه معیارهای دقت را متوقف می کند؛ شمار پوشش همچنان برای QC باقی می ماند. ساعت رکورد مشاهده از `observedAt` و برای بقیه از `receivedAt` است؛ این دو معنا را یکی نگیرید. روزهای بدون گزارش در میانگین پوشش وارد نمی شوند. شمار `n_independently_verified` وضعیت ثبت شده QC است؛ `n_eligible_independent_observations` نمونه دارای تطبیق قابل استفاده را جدا می شمارد و هویت همه گزارش ها همچنان ناشناس است.

`SYNTH-` در ابتدای reportId یا `synthetic:true` فقط داده آزمون است و پیش فرض حذف می شود. `--include-synthetic` فقط برای پوشه آزمون جداگانه است و خروجی آن برچسب آزمون دارد؛ با بازخورد واقعی ترکیب نشود. ابزار نمی تواند داده ساختگی بدون برچسب را کشف کند. تست ها فقط داخل scratch داده مصنوعی می سازند و شواهد میدانی تولید نمی کنند.

## قرارداد سخت گیرانه بازبینی مستقل

این قرارداد داخلی، تکمیل سخت گیرانه فرم حداقلی review در API-CONTRACT است؛ review قدیمی با status و basis به تنهایی برای معیار زمانی پذیرفته نیست. هر خط `reviews.jsonl` دقیقا این فیلدها را دارد:

| فیلد | قاعده |
| --- | --- |
| `schema` | عدد 1 |
| `reviewId` | شناسه یکتای بازبینی، الگوی `[A-Za-z0-9-]{16,64}` |
| `revision` | عدد 1 تا 1000؛ زنجیره هر reportId از 1، پیوسته و بدون تکرار |
| `reportId` | شناسه دقیق گزارش خام؛ نه شناسه مشابه یا حدسی |
| `status` | `independently_verified`, `rejected`, `needs_followup` |
| `reviewer` | شناسه داخلی غیرشخصی با الگوی `[A-Za-z0-9_.:-]{1,128}` |
| `reviewedAt` | ISO با offset؛ revision بعدی باید زمان متاخر داشته باشد |
| `method` | `independent_field_observation`, `independent_platform_record`, `documented_qc` |
| `basis` | ارجاع کوتاه داخلی به شاهد مستقل، ۱ تا ۲۰۰ کاراکتر؛ بدون اطلاعات شخصی |
| `split` | دقیقا `calibration` یا `held_out` مطابق قاعده ثابت پایین |
| `evidence` | `null` یا شیء دقیق تعریف شده پایین |

`evidence` دقیقا شامل `reportId`, `tripId`, `line`, `direction`, `stationId`, `serviceDate`, `event`, `observedAt`, `modelEventAt`, `modelVersion`, `platformReady` است. جهت فقط `out/back`، رخداد فقط رسیدن یا حرکت واقعی قطار و زمان ها با offset صریح هستند. همه شناسه ها و رخداد و زمان مدل باید با همان گزارش و حرکت دقیق تطبیق داشته باشند؛ زمان مستقل مشاهده در این نسخه محافظه کارانه باید با زمان ادعاشده برابر باشد. مدل دوباره اجرا یا زمان تطبیق یافته از روی ادعا حدس زده نمی شود. `documented_qc` به تنهایی شاهد مستقل زمانی نیست؛ evidence خالی هم معیار تولید نمی کند.

افزونه policyVersion=3: در evidence فیلد اختیاری `timePrecision` با `minute/second/unknown` مجاز است. نبود آن معادل unknown است: review خوانده و شمارش می شود ولی **به معیار زمانی راه پیدا نمی کند**. برای معیار، بازبین باید وضوح زمانی شاهد مستقل را صریحا minute یا second ثبت کند؛ مقدار فرستنده، تعداد رقم های ساعت یا status به تنهایی جای آن را نمی گیرد. خروجی معیار این نسخه همچنان با برچسب محافظه کارانه `precision:minute` است؛ واحد MAE/P90 ثانیه است اما ادعای وضوح ثانیه ای نیست، حتی اگر شاهد second باشد. شرط قدیمی precision خام برابر minute هم حفظ شده است؛ رکورد پیش فرض approximate صرفا با timePrecision ادعاشده به معیار ارتقا نمی یابد.

`platformReady` پیش فرض `null` است. در صورت وجود، دقیقا `{observedAt, method, basis}` دارد؛ method فقط یکی از دو روش مستقل، basis ارجاع به شاهد مستقل آماده بودن روی همان سکو است. خوداظهاری `outcome.platformReadyAtEpoch` جای آن را نمی گیرد. بازبین مسئول بررسی واقعی استقلال و مرجع زمان است؛ صرف نوشتن JSON یا انتخاب status استقلال را اثبات نمی کند.

در policyVersion=3، platformReady هم فیلد اختیاری `timePrecision` با همان سه مقدار دارد؛ برای نرخ missed train، وضوح شاهد مستقل آماده بودن باید صریحا minute یا second باشد. نبود آن فقط شاهد با وضوح نامعلوم است و در نرخ وارد نمی شود.

زنجیره revision با شناسه تکراری، شکاف revision، زمان نامرتب، split نادرست یا بازبینی نامعتبر به معیار راه پیدا نمی کند. revision جدید رکورد خام را تغییر نمی دهد. تاریخچه قبلی تا پایان retention حفظ می شود؛ «آخرین خط برنده است» وجود ندارد.

## مرز معیار و چرخه QC

1. ingest اختیاری و دارای رضایت → نگهداری ادعای خام → کنترل خرابی، تکرار و زمینه → مشاهده مستقل → بازبینی نسخه دار.
2. split پیش از تحلیل: اولین بایت `sha256(reportId + "|r2apb-split-v1")` اگر کمتر از 179 باشد `calibration`، وگرنه `held_out`. split در بازبینی باید همین باشد؛ تغییر دستی آن معتبر نیست. این تقسیم به تنهایی استقلال نمونه یا نبود سوگیری را تضمین نمی کند. از مشاهده نتیجه held-out برای تنظیم مدل استفاده نکنید.
3. نسخه های تکراری یک reportId یک بار شمارش می شوند، ولی هیچ کدام وارد معیار نمی شوند. گزارش های متعدد از یک رخداد همان سفر هم نمونه مستقل محسوب نمی شوند. held-out دارای سفر مشترک با calibration، حتی در ایستگاه دیگر، از معیار حذف می شود.
4. MAE/P90 فقط از حداقل ۳۰ مشاهده train_arrival/train_departure در held-out، با بررسی مستقل و تطبیق دقیق سفر، خط، جهت، ایستگاه، رخداد و نسخه مدل محاسبه می شود. precision باید `minute` باشد؛ اختلاف از زمان مستقل و زمان مدل بازحساب و با delta ذخیره شده کنترل می شود. P90 روش nearest-rank دارد. کیفیت minute هنوز دقت ثانیه ای نمی سازد و این خروجی فقط تحلیل آزمایشی است. داده کیفی، تطبیق ناموجود، جهت نامعلوم، نسخه ناهمخوان، تکرار، ردشده و بررسی نشده وارد MAE/P90 نمی شود.
5. `boarding_outcome` فقط شمار کیفی `made_it/missed/unknown` است، نه خطای مدل و نه نرخ missed train. معیار محافظه کارانه missed train فقط از مشاهده مستقل **حرکت قطار** با شاهد مستقل آماده بودن روی سکو به دست می آید: زمان آماده بودن حداکثر زمان حرکت مدل، فاصله شاهد آماده بودن و حرکت واقعی حداکثر یک ساعت؛ صورت کسر مواردی است که قطار پیش از آماده بودن مستقل حرکت کرده است. این «فرصت سوار شدن مدل که با حرکت زودهنگام از دست رفته» است، نه نتیجه شخصی سوار شدن یا ارزیابی دسترسی ورودی تا سکو. بدون این شواهد یا کمتر از ۳۰ نمونه، نرخ چاپ نمی شود.
6. پیشنهاد کالیبراسیون فقط در شاخه آزمایشی → ارزیابی held-out دست نخورده → بررسی مالک → انتشار مجاز بعدی. هیچ مرحله این CLI timetable، تقویم، وضعیت live یا Gate مسدود R2b را تغییر نمی دهد.

## retention و حذف؛ فقط ساخت snapshot جدید

پیش فرض retention برابر ۳۰ روز از `receivedAt` با cutoff نیمه شب UTC است؛ رکورد دقیقا روی cutoff حفظ می شود. شمارنده رد شدن فقط وقتی کل ماه قبل از cutoff است کنار گذاشته می شود. پاک سازی خودکار یا cron وجود ندارد.

```bash
# Dry run; source is never modified.
python -B scripts/beta_feedback_report.py purge --dir "$SNAPSHOT" --today YYYY-MM-DD
python -B scripts/beta_feedback_report.py delete-report --dir "$SNAPSHOT" --report-id "$REPORT_ID"
# Explicit publication of a NEW pruned snapshot; not in-place deletion.
python -B scripts/beta_feedback_report.py purge --dir "$SNAPSHOT" --today YYYY-MM-DD \
  --apply --out-dir "$OUTPUT/retained-store"
python -B scripts/beta_feedback_report.py delete-report --dir "$SNAPSHOT" --report-id "$REPORT_ID" \
  --apply --out-dir "$OUTPUT/deleted-store"
```

`--apply` بدون `--out-dir` رد می شود. مقصد باید جدید، بیرون ورودی و زیر پوشه ای بدون مجوز نوشتن گروه یا عموم باشد. همه فایل ها و تمام revision های مرتبط داخل staging خصوصی ساخته، fsync و سپس با یک rename پوشه منتشر و بازخوانی می شوند. شکست پیش از انتشار، snapshot اصلی را دست نخورده می گذارد. بایت رکوردهای باقی مانده و تاریخچه QC نگه داشته می شود؛ `operations.jsonl` با schema و policyVersion و hash و شمار حذف ها افزوده می شود، بدون note یا شناسه خام هدف. ورودی خراب، فایل ناشناخته و QC ناخوانا باعث توقف می شود؛ چیزی بی صدا حذف نمی شود.

فرمان maintenance، حتی dry run، lease اختصاصی `.feedback.lock` را با `O_EXCL`، مجوز 0600 و قالب PID:nonce ذخیره ساز می گیرد و تا پایان نگه می دارد. snapshot ورودی باید متعلق به کاربر جاری با مجوز 0700 باشد؛ اجداد قابل نوشتن توسط گروه یا عموم، alias نامطمئن و symlink در خود پوشه نهایی رد می شوند. تنها lock ساخته شده همین اجرا، پس از کنترل هویت، آزاد می شود؛ lock تعویض شده یا باقی مانده از اجرای قبلی دست نخورده می ماند. بنابراین dry run هیچ داده ماندگاری نمی نویسد، اما ایجاد و آزاد کردن این lease می تواند mtime پوشه را عوض کند.

در snapshot جدید، به offset هر روز UTC به تعداد سطر خام کنار گذاشته شده همان روز افزوده می شود؛ offset های موجود، حتی روزهای قدیمی، محافظه کارانه حفظ می شوند. عبور از سقف روز یا اندازه metadata عملیات را متوقف می کند و با دور ریختن شمارنده حل نمی شود. lock به مقصد کپی نمی شود. checksum ورودی quota و فهرست فایل ها را هم پوشش می دهد؛ تغییر ورودی پیش از انتشار متوقف می شود. سطر خام بدون newline نهایی، خط خالی و ماه ناسازگار با receivedAt خراب محسوب می شوند. `sourceUnchanged:true` به معنی حفظ بایت داده و مجوز فایل های منبع است؛ `sourceDeletionPerformed:false` صریحا می گوید حذف از منبع انجام نشده است. `removedReports` فقط سطرهای کنار گذاشته شده از خروجی پیشنهادی یا snapshot جدید است، نه حذف واقعی کاربر از همه نسخه ها.

**snapshot تحلیلی، جایگزین مستقیم پوشه runtime نیست.** Node فعلی `operations.jsonl` و `purge-log.jsonl` را ورودی ذخیره ساز نمی پذیرد. در ترفیع مجاز و مستقل مالک باید تاریخچه عملیات بیرون runtime بماند و فقط فایل های مجاز Node، شامل quota.json بدون reset، به یک کپی خصوصی جدید منتقل شوند؛ snapshot و تاریخچه قبلی حذف نشوند. CLI این ترفیع، جایگزینی پوشه فعال یا فراخوانی متدهای حذف در store زنده را انجام نمی دهد. تست integration فقط در scratch، رکوردها را با validateFeedback/toStored/append واقعی کد جاری تولید می کند و سپس کپی runtime جداگانه را باز می کند؛ سهمیه دو intake پس از کنار گذاشتن یکی همچنان full می ماند.

**ساخت snapshot جدید حذف از منبع، backup یا export قدیمی نیست.** جایگزینی store فعال، هماهنگی با writer و cache شناسه های Node و کنار گذاشتن امن نسخه ها، backup ها و خروجی های قبلی فقط عملیات مستقل مالک در پنجره آفلاین است و این ابزار آن را اجرا نمی کند. فایل های metadata/lock ذخیره ساز فعال به صورت حدسی بازنویسی نمی شوند. تا انجام این مرحله، درخواست حذف واقعی کامل نشده است. روی Production یا داده واقعی، هیچ purge/delete در این کار اجرا نشده است.
