# نتایج benchmark برنامه ریز Beta (R2a-PB)

بودجه ها پیش از هر اجرا در `PERFORMANCE-BUDGET.md` ثبت شده بودند و در هیچ مرحله ای تغییر نکرده اند. این سند همه اجراها را، از جمله اجراهای ناموفق، نشان می دهد.

## روش اندازه گیری و اجراها

- ابزار: `scripts/benchmark-journey-beta.mjs 100`؛ سرور واقعی روی loopback، مدل واقعی R1/R2a، بدون Production و بدون provider بیرونی.
- محیط: `systemd-run` با `MemoryMax=192M`، `MemorySwapMax=0`، `TasksMax=64`؛ Node `v22.23.4`؛ دستگاه ۴ هسته ای مشترک با سرویس های دیگر.
- ۱۰۰ نمونه برای هر فاز؛ فاز ها: baseline API قدیمی، cold، warm، concurrency دو، cache churn، API قدیمی هم زمان با برنامه ریز، ثبت بازخورد، burst، بازگشایی store نزدیک سقف، خطای مدل و خطای ذخیره ساز.
- داده بازخورد benchmark کاملاً ساختگی و در پوشه موقت خصوصی بود؛ شاهد میدانی نیست.

### اجرای نخست (روش v2، client و server در یک process): `BUDGET_MISSED`

سه بودجه رد شد:

- افزایش p95 API قدیمی در بار ترکیبی: ۳۲.۹ms در برابر سقف ۳۰ms
- event loop p95: ۳۴.۳ms در برابر سقف ۳۰ms
- بازگشایی store نزدیک سقف: ۵۵۷ms در برابر سقف ۵۰۰ms

اجرای دوباره همان روش (v2) در همان روز نیز `BUDGET_MISSED` بود (افزایش ۴۰.۱ms، event loop p95 ۳۰.۴ms). نتیجه v2 پنهان یا حذف نشده است؛ هر دو فایل در checkpoint خصوصی هستند.

### ریشه یابی (profile واقعی CPU)

1. **روش اندازه گیری:** در v2 کد client بار هم در همان event loop سرور اجرا می شد و تأخیر آن به سرور نسبت داده می شد. روش v3 سرور را در process فرزند جدا می گذارد، client در process والد است و هر دو در یک cgroup ۱۹۲MiB هستند.
2. **هزینه واقعی سرور (ایرادی در خود محصول):** هر درخواست برنامه ریز ۲۹.۷ms CPU همزمان می خواست. profile نشان داد:
   - `tehranParts` برای هر فراخوانی یک `Intl.DateTimeFormat` تازه می ساخت (حدود ۲۳٪ زمان)؛
   - snapshot امنیتی روز مدل برای منبع داخلی هم در هر درخواست از نو اعتبارسنجی می شد (حدود ۲۰٪ و بیشتر).
3. **اصلاح ها (بدون تغییر بودجه یا شل کردن تست):**
   - formatter زمان تهران یک بار ساخته می شود؛ خروجی بایت به بایت برابر است.
   - برای **فقط منبع داخلی** که روزهایش با `Object.freeze` عمیق و cache شده است، snapshot اعتبارسنجی شده برای همان object بازاستفاده می شود. هر منبع تزریقی یا خارجی همچنان در هر درخواست کامل اعتبارسنجی می شود؛ حتی اگر پرچم روشن باشد، object قابل تغییر هرگز بازاستفاده نمی شود (تست mutation اثبات شد: با حذف شرط frozen تست شکست می خورد).
   - تکه های خواندن store با ۱۲۸KiB به جای ۱۶KiB خوانده می شوند؛ سقف حافظه همچنان کوچک و محدود است.
   - هزینه هر درخواست برنامه ریز از حدود ۲۹.۷ms به حدود ۶ms رسید.
4. fingerprint مدل (`modelVersion`) از محتوای ماژول های مسیر مدل مشتق می شود؛ تغییر `time.ts` آن را از `sha256:51ce05b4…` به `sha256:316fddaf…` تغییر داد. رفتار زمانی تغییر نکرد (Oracle ۵۱۸۴ پرسش و تست های زمان سبز ماندند)، اما بازخوردهایی که با version قبلی ثبت شده باشند «model_version_mismatch» می شوند. تا امروز هیچ بازخورد واقعی ثبت نشده است.

## محدودیت ها

- نمونه کوتاه ۱۰۰ تایی روی دستگاه مشترک است و SLO نیست؛ نوسان زمان بین اجراها دیده شده است (warm در یک بازه پرکار دستگاه در v2 تا ۳۳ms رسید).
- event loop p95 حدود ۲۵ms است، یعنی حدود ۱۷٪ زیر سقف؛ مجموعه کار churn (ساخت روز مدل تازه) مسدودکننده است. این حاشیه کم است و پایش ۲۴ ساعت نخست الزامی است.
- بازگشایی store نزدیک سقف ۴۱۵ تا ۴۵۳ms است، یعنی ۱۰ تا ۱۷٪ زیر سقف؛ فقط در راه اندازی مجدد رخ می دهد.
- ظرفیت زیر «دو کار هم زمان» طراحی شده است؛ این قابلیت برای مقیاس عمومی شهر ضمانت نمی شود و فشار اضافه عمداً `429` می گیرد.
- provider در benchmark همان مدل درون process است، نه سرویس بیرونی زنده.
