## ۱. جمع بندی تصمیم های پیشنهادی

### برداشت نهایی از محصول

بِسراه باید «تصمیم یار زندگی روزمره» باشد: کاربر را برای رسیدن به انتخاب مناسب از نظر هزینه نهایی، زمان، مطلوبیت، محدودیت و عدم قطعیت همراهی کند؛ به تدریج و با رضایت او شناخت پیدا کند؛ سپس در آینده برخی کارهای تکراری را در حدود مجوز مشخص انجام دهد. رفت و آمد، خوراک و خرید سه دامنه این هدف اند، نه سه پروژه بی ارتباط و نه صرفاً سه کارت در صفحه اصلی.

### پیشنهاد معماری

1. **معماری Node.js/TypeScript فعلی حفظ شود؛ یک modular monolith با مرزهای روشن اضافه شود.** ساخت شش سرویس مستقل، مهاجرت framework، پایگاه برداری، صف توزیع شده یا بازنویسی موتور مترو برای MVP توجیه فعلی ندارد.
2. **اولین خروجی، کتابخانه تصمیم گیری قطعی و یک پایلوت محدود Transit باشد.** ابتدا برنامه سفر ایستگاه به ایستگاه با داده واقعی موتور موجود؛ سپس کریدور محدود A→B با مسیر پیاده، ورودی ایستگاه، تعرفه و زمان تعویض اعتبارسنجی شده.
3. **جدول رسیدن قطار با موتور سفر A→B یکی نیست.** داده stop-time قابل استفاده داریم؛ اتصال پیاده، تعویض، تقویم و تعرفه هنوز کامل نیست.
4. **برای اتوبوس، کشف مسیر ساختاری ممکن است؛ ETA رقابتی فعلاً پشتوانه ندارد.** داده نام ایستگاه یا هندسه OSM به تنهایی زمان حرکت یا امکان تعویض را اثبات نمی کند.
5. **هسته مشترک بر قرارداد شواهد و محدودیت ها بنا شود، نه بر یک مدل زبانی.** مدل زبانی بعداً ورودی را ساختارمند و دلیل های تأییدشده را قابل فهم می کند؛ عدد، صلاحیت، مجوز یا قیمت نمی سازد.
6. **حافظه محلی صریح پیش از حافظه استنباطی یا سروری بیاید.** تاریخچه بازدید فعلی، Memory Engine محصول نیست. برای همگام سازی سروری، احراز هویت و مالکیت داده پیش نیازند.
7. **بسفود موجود حفظ شود، اما شواهدش بازتعریف شوند.** کاتالوگ ایستا، وضعیت باز بودن، موجودی غذا، پوشش ارسال و قیمت نهایی پنج موضوع متفاوت اند.
8. **بسپی طبق چشم انداز جدید، حوزه خرید و مقایسه شرایط واقعی است، نه الزاماً کیف پول.** فعلاً آداپتور خرید، BNPL یا اجرای پرداخت ندارد.
9. **هیچ الزام نمایشی برای سه گزینه متفاوت وجود نداشته باشد.** خروجی معتبر می تواند صفر، یک یا چند گزینه باشد. یک گزینه ممکن است چند عنوان مستند بگیرد؛ گزینه ساختگی برای پر کردن سه کارت تولید نشود.
10. **پیش از توسعه، شکاف بازتولید اتوبوس و شناسنامه انتشار بسته شود.** HEAD فعلی به تنهایی نماینده محصول منتشر شده نیست.

**نقطه شروع پیشنهادی برای تأیید:** مرحله R0 و سپس R1 این سند؛ یعنی تثبیت خط مبنا و قراردادهای خالص، بدون تغییر UI و بدون API عمومی جدید. افزودن رفتار جدید فقط پس از تأیید جداگانه.

## ۲. روش بررسی، اعتبار و محدودیت شواهد

شواهد در این گزارش چهار نوع دارند:

- **کد:** ارجاع `file:line` به نسخه کاری بررسی شده؛ با تغییر فایل، شماره خط ممکن است تغییر کند.
- **داده:** شمارش مستقیم JSON و SQL فقط خواندنی، نه صرفاً عددهای README یا metadata.
- **زمان اجرا:** وضعیت systemd، مقایسه byte/hash فایل های کاری و مستقر و HTTP واقعی.
- **پیشنهاد:** طراحی، سقف منابع، معیار پذیرش و برنامه آینده؛ هیچ کدام ادعای قابلیت فعال نیست.

SQLite با `mode=ro` و `PRAGMA query_only=ON` بررسی شد. داده تماس، token، credential، آدرس خصوصی حساب و محتوای شخصی در گزارش کپی نشده است.

### محدودیت های این ممیزی

- مشاهده مرورگر، تأیید گوشی واقعی یا Telegram WebView نیست.
- آزمون محلی درست بودن رفتار نسبت به مدل را نشان می دهد؛ دقت واقعی ETA را ثابت نمی کند.
- GET موفق ارائه دهنده تضمین SLA، تازگی cache بالادست یا پایداری فردا نیست.
- فعال بودن workflow بات یا رسیدن پیام به تلگرام در این مرحله با ارسال واقعی جدید آزمایش نشد؛ شواهد بات در این گزارش کد و تست های workflow است، نه تأیید دوباره تحویل پیام.
- فایل `BESRAH-SUPERAPP-PLAN.md` که در سند ورودی نام برده شده، در محدوده اسناد پروژه و پیوست های Markdown بررسی شده پیدا نشد؛ محتوای آن حدس زده نشده است.
- داده میدانی جدید جمع آوری نشده است. معیار «۲۰ سفر مستقل» هنوز برآورده نشده است.

## ۴. Intelligence Core امروز: موجود، جزئی یا غایب؟

| قابلیت | وضعیت واقعی | چیزی که می توان بازاستفاده کرد | چیزی که هنوز نداریم |
|---|---|---|---|
| Context Engine | ابتدایی و پراکنده | زمان تهران، نوع روز، درخواست ایستگاه، موقعیت موقت، state رابط | snapshot مشترک، دقت/عمر مکان، مجوز هدفمند، قرارداد context |
| Memory Engine | موجود نیست؛ storage محلی محدود داریم | علاقه مندی، ایستگاه اخیر، تنظیمات ظاهر، سرویس ذخیره شده | ترجیحات دامنه ای، provenance، رضایت یادگیری، انقضا، اصلاح/حذف جامع، sync |
| Decision Engine | در سطح سراسری موجود نیست | قواعد زمانی قطعی مترو و فیلترهای محلی | قیود چنددامنه ای، مقایسه هزینه/زمان، feasibility، سیاست داده مجهول |
| Recommendation Engine | محصولی و مشترک نیست | مرتب سازی مکانی بسفود، قالب توضیح، prototype تحقیقاتی | جبهه پارتو، مقایسه هم ارز، دلایل با ارجاع فکت، سؤال اثرگذار |

### ۵.۱ مترو

### ۶.۱ مترو: چه چیزی واقعاً داریم؟

- **۳۶ ایستگاه فیزیکی شناسه دار** در `network.json`، با مختصات.
- خط ۱ دارای ۲۴ عضویت و خط ۲ دارای ۱۳ عضویت است؛ شریعتی مشترک است. ۲۴ + ۱۳ به معنی ۳۷ ایستگاه مستقل نیست.

- مختصات موجود، ورودی پیاده، سکوی دقیق یا مسیر تعویض نیستند.

### ۶.۲ کیفیت زمان ها

- خط ۱ جمعه: فاز اندازه گیری شده برای همان مبنای میدانی.
- پنجشنبه: ترکیبی از یک سفر ثبت شده، برگه و فرض سرفاصله؛ برخی قطعات اندازه گیری نشده با ضریب 1.073 مقیاس می شوند (`network.ts:80–91`).
- روز عادی: فاز حرکت اندازه گیری نشده (`engine.ts:68–78`).
- بسیاری از زمان های برگشت از تقارن با رفت ساخته می شوند (`network.ts:37–50`)؛ این ها اندازه گیری مستقل نیستند.
- مسیر توسعه فرودگاه و برخی توقف ها مشتق/فرضی اند؛ `live=false` باقی می مانند.
- خط ۲: ۸ قطعه legacy و ۴ قطعه اندازه گیری شده؛ فاز هر دو جهت فرضی است. سرفاصله روز عادی تصمیم مالک ۱۰ دقیقه در برابر ۱۲ دقیقه منبع بایگانی است (`line2.ts:5–11,51–75` و `network.json:973–1015`).

**نتیجه:** جدول مدل شده برای تولید candidate سفر قابل استفاده است، اما زمان قطعی یا تضمین رسیدن به موعد را پشتیبانی نمی کند. بازه خطا نیز بدون کالیبراسیون مستقل، نباید با درصد اطمینان ساختگی عرضه شود.

### ۶.۳ چرا نباید planner را روی `/next` بسازیم؟

خروجی تابلو (`service.ts:8–27,109–142`) برای نمایش است: ETA گرد شده و ساعت محلی دارد و trip ID، departure epoch و stop sequence کامل را نگه نمی دارد. علاوه بر این، `nextPasses` در خط ۱ و ۲، قطاری را که ورودش گذشته ولی هنوز روی سکو است حذف می کند (`engine.ts:201–203`، `line2.ts:125–127`).

برای سوارشدن باید departure و امکان boarding بررسی شود، نه فقط arrival. بنابراین:

- API فعلی برای سازگاری حفظ شود.
- آداپتور سفر از timed stops خام استفاده کند.
- پایین دست برچسب ردیاب یا جابه جایی بصری نشانگر را به عنوان مکان یا زمان سفر مصرف نکند.

هندسه موجود هم مساوی شبکه قابل پیمایش نیست: ممیزی ذخیره شده در `research/bus-static-completion/audit/route_geometry_metrics.json`، ۳۵ route چندمولفه ای و تنها ۱۴۲ route از ۱۸۰ با زنجیره پیوسته member-order را گزارش می کند؛ turn restriction یا صحت رانندگی/پیاده روی را تأیید نمی کند.

### ۶.۵ نتیجه عملی A→B

سه سطح باید جدا باشند:

1. **اکنون از نظر کد قابل ساخت:** سفر مدل شده ایستگاه به ایستگاه روی یک خط؛ بدون ادعای هزینه و پیاده روی کامل.
2. **با داده محدود تازه:** یک کریدور A→B شامل مسیر پیاده اعتبارسنجی شده، ورود/خروج و در صورت لزوم انتقال شریعتی؛ ETA با عدم قطعیت قابل توضیح.
3. **بعداً:** چندوجهی مترو + اتوبوس + پیاده با timetable/فرکانس معتبر، و تاکسی تنها با quote و زمان قابل اتکای همان درخواست.

### ۷.۲ چه چیزی در runtime تأیید شد؟

در مرورگر واقعی سرور، صفحه بسفود بارگذاری شد، چهار نتیجه پیش فرض اطراف مرجع وکیل آباد، منو، نشانی موجود و لینک نقشه دیده شد. مشکل عمومی بارگذاری در آن نمونه بازتولید نشد؛ این بررسی همه حالت های شبکه یا permission را پوشش نمی دهد.

### ۷.۳ شکاف های فعلی و قابل اصلاح پیش از توصیه اقتصادی

- حداقل سفارش با «هزینه غذا + ارسال + کارمزد» متفاوت است؛ فیلتر زیر ۱۵۰ هزار تومان فعلی حداقل سبد را می سنجد، نه سقف کل پرداخت.

- قیمت، stock، پوشش مقصد، delivery fee و applicability تخفیف باید جداگانه ثبت شوند.
- کاتالوگ کامل در startup هسته synchronous خوانده می شود (`server.ts:15`)؛ خرابی غذای غیرضروری نباید Transit را از بالا آمدن بازدارد.
- map فروشگاه در route وضعیت فقط در startup ساخته می شود، ولی فایل کاتالوگ در سرو static قابل refresh است؛ نسخه های ناسازگار ممکن است به وجود بیایند.
- rate limit تپسی، process-global و vendor-global است؛ یک مصرف کننده می تواند سهم دیگران را کاهش دهد.
- صفحه خطای بارگذاری retry مستقیم ندارد (`food.js:180–187,323–344`).
- generator کامل و versioned برای انتشار کاتالوگ فعلی در مسیرهای پروژه بررسی شده تثبیت نشده است؛ pipeline باید بازتولیدپذیر شود.

### ۷.۴ مشکل مهم context مکانی

`food.js:6–44` هنوز ۳۷ ورودی ایستگاه hardcoded دارد، در حالی که مرجع مترو ۳۶ ایستگاه است. این فهرست با `network.json` یکی نیست و نباید وارد هسته مشترک شود. وجود دستور درست در skill یا توضیح قبلی، به معنی اعمال آن در کد نیست.

## ۹. معماری هدف حداقلی و مرز شش قابلیت

```text
Mini App / Web / Bot
       ↓ ورودی ساختارمند؛ بدون اختیار ساخت userId/permission

       ↓
ContextResolver ← PreferenceResolver (محلی/صریح در ابتدا)
       ↓
DecisionService / orchestrator
       ├─ TransitAdapter → timetable فعلی + planner محدود

       ↓

       ↓

       ↓
Recommendation + factual explanation + at most one useful question
       ↓
انتخاب / handoff / feedback اختیاری
       ↓
Memory repository با consent (پس از مرحله مربوط)

Automation: خارج از مسیر MVP؛ بعداً با gate اجرای مستقل
```

```text
    trips.ts           # index شناسه، occurrence و روز خدمت
    plan.ts            # مسیر time-dependent محدود
    transfers.ts       # پیوندهای انتقال دارای منبع
    access.ts          # مسیر پیاده/ورود؛ فقط با داده معتبر
  profiles/            # مرحله بعد؛ فعلاً interface طراحی
  automation/          # مرحله بعد؛ فعلاً ساخته نشود
```

این تعداد نام فایل تعهد به ایجاد فایل های خالی نیست. implementation کوچک می تواند فایل ها را ترکیب کند؛ مرز مسئولیت مهم تر از تعداد فایل است. هیچ framework یا package جدید صرفاً برای این نام ها لازم نیست.

### وابستگی ممنوع

- optimizer به DB، HTTP provider یا DOM وابسته نشود.
- provider حق رتبه بندی تجاری مخفی یا نوشتن preference نداشته باشد.
- explain عدد جدید تولید نکند؛ فقط metric/reason معتبر را مصرف کند.
- memory از مشاهده ساده به صورت خودکار رضایت یا محدودیت حساس نسازد.
- LLM نتواند URL آزاد fetch، سقف پرداخت یا مجوز اجرا تعیین کند.
- Automation Engine با flag روی Recommendation فعال نشود؛ اجرای واقعی boundary جدا دارد.

## ۱۰. قراردادهای داده پیشنهادی نسخه ۱٫۱

اسکچ زیر قرارداد طراحی است، نه کد وارد شده به محصول و نه schema نهایی تصویب شده.

### ۱۰.۱ شواهد در سطح مقدار

```ts
type EvidenceRef = {
  sourceId: string;
  kind: 'official' | 'field' | 'provider' | 'osm' | 'derived' | 'user';
  observedAt?: string;
  retrievedAt?: string;
  ingestedAt?: string;
  validUntil?: string;
  dataVersion: string;
  scope: { serviceDate?: string; pointRef?: string; basketRef?: string };
  quality: string; // categorical؛ تا کالیبراسیون، احتمال عددی نیست
  live: boolean;
  derivedFrom?: string[];
  methodVersion?: string;
};

type Metric<T> =
  | { state: 'known'; value: T; evidence: EvidenceRef[] }
  | { state: 'estimated'; value?: T; interval?: { min: T; max: T };
      evidence: EvidenceRef[]; assumptions: string[] }
  | { state: 'unknown' | 'stale' | 'not_applicable'; reason: string };
```

در schema نهایی، `estimated` باید حداقل value یا interval معتبر داشته باشد. بازه نیز evidence/روش می خواهد؛ تولید بازه با ضرب حدسی ممنوع است. `stale` در لایه مقایسه مقدار معتبر ندارد؛ اگر لازم بود مقدار گذشته با برچسب فقط نمایشی جدا حمل شود.

- پول: integer تومان با اجزای subtotal/delivery/fee/discount؛ مجموع فقط وقتی همه اجزای لازم معلوم و سازگارند.
- زمان داخل planner: epoch seconds با نام فیلد صریح و serviceDate؛ در API timestamp با offset و timezone جدا. زمان میلی ثانیه UI با ثانیه موتور مخلوط نشود.
- فاصله: متر، walking duration مستقل از straight-line distance.
- کاتالوگ و تخمین برنامه ای با timestamp دریافت تازه، خودبه خود `live=true` نمی شوند.

### ۱۰.۲ Context و permission

دو مدل جدا:

1. **EvaluateRequest:** ورودی نامطمئن کاربر شامل دامنه، مبدأ/مقصد، زمان مجاز و override های صریح همان نوبت.
2. **ResolvedContext:** ساخته شده در مرز قابل اعتماد شامل requestId، actor/session واقعی، permission های تأییدشده، policyVersion و snapshot زمانی.

مکان موقت شامل `accuracyM`, `capturedAt`, `expiresAt`, `purpose`, `scope` باشد. شناسه خانه یا محل کار اختیاری و جدا از مختصات یک درخواست است.

**برای حفظ قاعده فعلی مکان روی دستگاه:** MVP ایستگاه به ایستگاه فقط شناسه ایستگاه ارسال کند. در مرحله دسترسی پیاده، یا محاسبه محلی روی داده محدود انجام شود، یا ارسال موقت مختصات به core با رضایت جداگانه و تصویب مالک اضافه شود. محاسبه مختصاتی سروری را نمی توان هم زمان «هیچ مختصاتی از دستگاه خارج نمی شود» نامید.

### ۱۰.۳ Candidate دامنه ای

قسمت مشترک: شناسه، domain، provider-qualified ID، task/equivalence group، metrics، evidence، caveat و capability.

قسمت های اختصاصی به صورت union حفظ شوند:

- Transit: legs، trip/stop occurrence، board/alight، انتظار، پیاده، تعویض، زمان ورود مدل، coverage.
- Food: vendor/item/variation/quantity، وضعیت فروشگاه، stock، محدوده ارسال، checkout quote و زمان اعتبار.
- Shopping: شناسه محصول و گونه، فروشنده، قیمت نقد، برنامه اقساط و همه اجزای پرداخت.

نمونه شناسه ها: `tapsifood:vendor:217xr2`؛ سفر `metro:2026-10-16:1:B-out-18`. شناسه تولیدی بر اساس نام رستوران یا code بدون منبع ساخته نشود.

availability تک پرچم نباشد: وضعیت برنامه ای سرویس، stock، پوشش مقصد و وجود quote جدا باشند. در سطح نتیجه، `eligible | ineligible | undetermined` حاصل gate سیاست است؛ «open» به تنهایی eligible برای سفارش نیست.

### ۱۰.۴ نتیجه و توضیح

```ts
type EvaluationState = 'ok' | 'partial' | 'insufficient_data' | 'no_feasible_option';
// علاوه بر گزینه ها:
// comparisonComplete, unknownObjectives, excludedReasons,
// evidence/data/policy versions, question?, inlineExplanation
```

توضیح هر ادعا به metric/leg/evidence اشاره کند. تا قبل از داشتن ownership، why داخل پاسخ برگردد؛ requestId تصادفی به تنهایی مجوز خواندن context خصوصی نیست.

### ۱۰.۵ ترجیح، سؤال و feedback

- `Preference` دارای scope، provenance، confirmedByUser، updatedAt، expiry و نسخه policy باشد.
- محدودیت سخت از ترجیح نرم جدا باشد؛ بودجه یا ممنوعیت غذایی به خاطر امتیاز بالا نادیده گرفته نشود.
- دستور فعلی می تواند ترجیح نرم همان نوبت را عوض کند؛ تغییر سقف دائمی یا مجوز پرداخت نیاز به عمل صریح دارد.
- `DecisionFeedback` نوع selected/dismissed/corrected/saved را دارد، ولی هر انتخاب علتش را ثابت نمی کند.
- سؤال فقط وقتی مطرح شود که پاسخ، انتخاب بین candidate های موجود را عوض کند؛ نبود timetable یا fee با سؤال سلیقه حل نمی شود.
- اجازه «همین بار»، «برای بعد ذخیره کن»، «رد کردن» حفظ شود. عدم پاسخ نباید سرویس ناشناس را بی فایده کند.

## ۱۱. طراحی الگوریتم سفر A→B بدون تخریب موتور

### ۱۱.۱ ساخت سفرها

1. timetable از موتور موجود برای روز خدمت مجاز و در صورت عبور از نیمه شب، روز مجاور لازم خوانده شود.
2. هر trip با تاریخ، خط و منبع namespace شود؛ شناسه فعلی روزانه به تنهایی یکتا نیست.
3. stop occurrence، ترتیب، arrival و departure واقعی مدل نگه داشته شود.
4. node های platform/line occurrence از node ایستگاه فیزیکی جدا باشند؛ شریعتی دو سکوی خطی و پیوند انتقال مشخص می خواهد.
5. edge پیاده و انتقال فقط با evidence وارد شود؛ فاصله هوایی جای طول مسیر پیاده قرار نگیرد.

### ۱۱.۲ امکان سوار شدن و انتقال

- boarding فقط وقتی مجاز است که زمان رسیدن به سکو + حاشیه لازم، از departure عبور نکند و trip در آن نقطه مسافر سوار کند.
- layover پایانه با توقف قابل boarding یکی نیست؛ نباید از `depart` آخرین stop به تنهایی اجازه سفر بعدی استخراج کرد.
- alight باید بعد از board روی همان trip باشد؛ شاخه مقصد و پایان سفر بررسی شود.
- انتقال به trip بعدی با زمان پیاده سکو، ورود/خروج و حاشیه متناسب با شواهد انجام شود.
- `arriveBy` با phase نامعلوم، تضمین قابل قبول تولید نمی کند؛ نتیجه undetermined یا estimate با هشدار است.
- برای فرکانس بدون فاز، می توان در آینده policy انتظار بازه ای داشت؛ انتظار میانگین نصف headway را نباید زمان قطعی قطار بعدی جا زد.

### ۱۱.۳ انتخاب الگوریتم

**تصمیم MVP:** برای یک خط و یک انتقال، enumeration محدود trip های دارای ترتیب stop، با reconstruction مسیر و آزمون oracle مستقل کافی است. این تصمیم اندازه مسئله است، نه اصرار بر الگوریتم اختصاصی همیشگی.

پس از تثبیت داده، connection های `from/to/depart/arrive/tripId` می توانند در یک scan زمان مرتب استفاده شوند. CSA مرجع مناسبی برای earliest arrival است؛ RAPTOR مرجع مناسب مقایسه زمان رسیدن و تعداد تعویض در شبکه چندخطی است. انتخاب نهایی بین آن ها بعد از benchmark روی داده خودمان انجام شود، نه صرفاً شهرت الگوریتم. [EXT-1، EXT-2]

- اگر CSA استفاده شد، minimum transfer و امکان ادامه همان trip باید صریح پیاده شود؛ یک برچسب earliest arrival ساده لزوماً همه ترجیحات آینده را نگه نمی دارد.
- اگر چندمعیاره شد، nondominated label ها با سقف محاسبات و reconstruction درست حفظ شوند.
- شبکه اتوبوس تا داشتن زمان یا frequency معتبر تنها برای candidate topology است و در قیاس سریع ترین وارد نمی شود.
- تاکسی بدون quote زمان/هزینه معتبر از مقایسه عددی خارج می ماند.

### ۱۱.۴ قاعده مقایسه اقتصادی

1. حذف نقض قید سخت؛ موارد قید نامعلوم جدا.
2. گروه بندی task و هم ارزی؛ غذاهای با مقدار متفاوت یا کالای variation متفاوت جایگزین دقیق نیستند.
3. objective set مشترک و ثابت: هزینه، زمان، پیاده، تعویض، مطلوبیتِ دارای شاهد.
4. Pareto فقط روی داده قابل مقایسه؛ هدف مجهول نه صفر، نه میانگین و نه مزیت خودکار است.
5. برای بازه ها، dominance محافظه کارانه تعریف شود؛ overlap بازه، برتری قطعی نیست.
6. رتبه «متعادل» فقط با سیاست توضیح پذیر و ترجیح/وزن آشکار؛ تبدیل زمان به پول با ضریب پنهان ممنوع.
7. بهترین در «مجموعه گزینه های قابل بررسی» با بهترین کل شهر فرق دارد؛ coverage خروجی مشخص شود.

## ۱۲. نمونه محاسبه شده از موتور فعلی و fallback سه انتخاب

این نمونه با **کد کامپایل شده موجود** و روز تاریخی مدل `2026-10-16` اجرا شد؛ خروجی، بازپخش مدل است، نه سفر انجام شده تازه، timetable امروز یا وعده زمان قطعی.

**فرض:** کاربر در ساعت ۱۴:۰۰:۰۰ تهران آماده سوارشدن در سکوی کوثر است و به شریعتی می رود. پیاده تا سکو، کرایه و خروج از مقصد در این نمونه وارد نشده اند.

| candidate واقعی مدل | حرکت مدل از کوثر | رسیدن مدل به شریعتی | انتظار مدل، ثانیه | حرکت روی trip، ثانیه | کل تا ایستگاه، ثانیه |
|---|---|---|---:|---:|---:|
| `B-out-18` | ۱۴:۰۵:۲۱ | ۱۴:۱۷:۵۲ | ۳۲۱٫۸ | ۷۵۱٫۱ | ۱۰۷۲٫۹ |
| `A-out-17` | ۱۴:۱۷:۱۲ | ۱۴:۲۹:۴۳ | ۱۰۳۲٫۸ | ۷۵۱٫۱ | ۱۷۸۳٫۹ |
| `B-out-19` | ۱۴:۲۹:۲۱ | ۱۴:۴۱:۵۲ | ۱۷۶۱٫۸ | ۷۵۱٫۱ | ۲۵۱۲٫۹ |

کاربر B/A نمی بیند؛ این ها شناسه داخلی سفر هستند. قطار اول و سوم مقصد فرودگاه دارند و از مقصد مورد نظر عبور می کنند؛ قطار دوم مقصد غدیر دارد و آن هم از شریعتی عبور می کند.

**خروجی درست در داده فعلی:** انتخاب اول از نظر زمان مدل زودتر است؛ دو حرکت بعدی فقط جایگزین زمانی اند و در اهداف معلوم مزیتی نشان نمی دهند. آن ها را برای تولید سه پیشنهاد متنوع نگه نمی داریم.

- سریع ترین: «زودتر رسیدن در مدل موجود»، همراه با عدم قطعیت و دامنه محدود.
- کم هزینه ترین: **نامشخص**، چون کرایه معتبر و مقایسه کامل موجود نیست.
- متعادل: ادعای مستقل نداریم؛ یا همان گزینه تحت سیاست روشن نشان داده می شود یا سؤال اثرگذار مطرح نمی شود چون بین این سه trip تفاوت ترجیحی مؤثری نداریم.

برای نمونه A→B کامل، پس از تأمین داده، سه ساختار ممکن برای بررسی عبارت اند از پیاده مستقیم، دسترسی پیاده + مترو، و مسیر با انتقال به خط دیگر. هر سه صرفاً وقتی نمایش داده می شوند که همان مبدأ/مقصد و داده معتبر داشته باشند و واقعاً تفاوت معنادار نشان دهند؛ تولید عدد پیاده یا کرایه برای تکمیل مثال ممنوع است.

**Fallback رسمی:**

- صفر مسیر معتبر: `no_feasible_option` یا `insufficient_data` با تفکیک علت.
- یک مسیر معتبر: یک پیشنهاد، نه سه کارت تکراری.
- داده هزینه ناقص: مقایسه هزینه متوقف، امکان نمایش زمان مدل با caveat.
- شبکه پیاده ناقص: station-to-station، نه ادعای دربه در.
- فاز نامعلوم: برآورد با کیفیت منبع؛ نه تضمین deadline.

## ۱۳. اشتراک هسته برای بسفود و بسپی

### Besfood

آداپتور فعلی دور کاتالوگ و وضعیت حفظ می شود. لایه جدید باید زمان observation و ingest، identity محصول/variation، stock و محدوده quote را از مرحله جمع آوری تا توصیه نگه دارد.

هزینه قابل مقایسه:

```text
سبد هم ارز + ارسال + همه کارمزدها − تخفیف واقعاً قابل اعمال
```

کارت رستوران می تواند discovery باشد، اما recommendation اقتصادی به basket/quote نیاز دارد. استعلام در نقطه خود رستوران برای حفظ حریم خصوصی مجاز فعلی است؛ اگر quote مخصوص مقصد بخواهیم، سیاست ارسال مقصد به provider باید جداگانه طراحی و تأیید شود. رضایت به location در مرورگر، رضایت به انتقال آن به همه ارائه دهنده ها نیست.

### Bespay / shopping

از همان Evidence، Constraint، Comparison، Explanation و Preference استفاده کند، اما metric های دامنه خود را نگه دارد:

- شناسه محصول/مدل/حجم/variation و فروشنده؛
- مبلغ نقد، ارسال، پیش پرداخت، مبلغ و زمان هر قسط، کارمزدها و شرایط مؤثر بر مجموع؛
- stock و محدوده اعتبار quote؛
- distinction بین صلاحیت اعتبار نزد ارائه دهنده و امکان مقایسه شرایط؛
- referral/handoff در ابتدا، نه نگهداری پول یا اجرای پرداخت.

لازم نیست برای مشترک شدن هسته، همه چیز به `quality: number` یا یک score مبهم تبدیل شود. مشترکات شواهد و سیاست تصمیم اند؛ جزئیات دامنه حذف نمی شوند.

مسیر عمومی `/api/*` به `/app/api/*` core نگاشت می شود. `deploy/nginx-besrah-miniapp.conf:11–26` فقط GET/HEAD را می پذیرد. POST آینده نیاز به location دقیق و محدود دارد؛ باز کردن کلی روش های نوشتن توصیه نمی شود.

- schema runtime برای request و response؛ TypeScript type به تنهایی validation زمان اجرا نیست. از امکانات schema موجود Fastify می توان استفاده کرد؛ dependency جدید فعلاً لازم نیست. [EXT-3]
- تاریخ/زمان آینده داخل body هم باید محدود شود؛ ممنوعیت `at` در query مانع body بزرگ یا بازه تاریخی planner نیست.
- خطاهای versioned مثل `unsupported_capability`, `insufficient_evidence`, `provider_timeout`, `invalid_context` با fallback روشن.
- response و log فاقد raw intent حساس، token، آلرژی یا مختصات دقیق باشند.
- `why/:requestId` پیش از ownership سروری عمومی نشود.

### حفظ UI و CSP

`miniapp.ts:95,123–125` CSP هم مبدأ و سخت گیر دارد؛ افزوده های JS باید در allowlist ثبت شوند. HM7 Commerce و skin فعلی دست نخورند؛ HM7 Panel فقط در صورت نیاز بعدی به عملیات، نه جایگزین UI مسافر. پاسخ explanation با text node رندر شود، نه HTML مدل یا provider.

### حافظه سروری آینده

واحد فعلی `ProtectSystem`/`ProtectHome` دارد. استفاده مستقیم production از SQLite تحقیق داخل `/root` یا باز کردن کلی دسترسی ممنوع است. در مرحله مربوط، state directory مجاز، schema version، migration، retention، backup و delete/export تعریف شود. SQLite ابتدا انتخاب قابل ارزیابی برای نوشتن محدود است؛ تغییر به سرویس DB دیگر فقط با نیاز concurrency/operational اثبات شده، نه به صورت پیش فرض اجباری.

**لاگ و حذف:** ذخیره نشدن access log عمومی، به معنی «هیچ داده ای هیچ جا ذخیره نمی شود» نیست؛ Telegram، n8n، backup، cache و پایگاه آتی هر کدام سیاست مستقل می خواهند. حذف منطقی، حذف نسخه پشتیبان و لغو consent از هم تفکیک شوند.

## ۱۶. برنامه مرحله ای اجرا و معیار پایان

ترتیب زیر dependency-based است؛ زمان تقویمی قطعی پیش بینی نشده، چون داده میدانی و اتصال provider هنوز پیش نیاز دارند. هر مرحله با گزارش شواهد و تأیید جداگانه مالک تمام می شود.

### R0 — خط مبنا و صحت داده

**کارها:** بازبینی و تفکیک تغییرات موجود، ثبت artifact/data hashes، اصلاح pipeline overlay اتوبوس، رفع دو تست شکست خورده بدون حذف اصلاحات، مشخص کردن freshness/coverage، برنامه رفع context مکانی بسفود و startup coupling.

**تحویل:** capability matrix نسخه دار، release manifest، source/overlay شفاف و test baseline بدون شکست حل نشده مرتبط.

**پذیرش:** عدد metadata برابر محتوای واقعی؛ builder در `--check` موفق؛ هیچ source خام بازنویسی نشده؛ difference انتشار معلوم؛ خرابی غذای اختیاری Transit را پایین نیاورد.

### R1 — کتابخانه قرارداد و تصمیم بدون API/DB/UI جدید

**کارها:** Evidence/Metric، domain candidates، Context، hard constraints، ComparableGroup، Result؛ validators و pure comparator؛ توضیح مبتنی بر reason code و سؤال اثرگذار.

**تحویل:** کتابخانه TS و fixture های کاملاً علامت گذاری شده؛ هیچ candidate واقعی از fixture به UI عمومی نرود.

**پذیرش:** تست صفر/unknown/stale، namespace، interval، hard constraint، incomparable، نتیجه خالی و چند label برای یک گزینه؛ بدون DB جدید، LLM اجباری یا تغییر موتور.

### R2a — پایلوت داخلی سفر مترو ایستگاه به ایستگاه

**کارها:** adapter timed trip خط ۱ و ۲، day-qualified ID، same-trip، boarding/departure، انتقال فقط با داده/assumption آشکار، handling روز مجاور و تعطیلات.

**تحویل:** query داخلی/تست برای کریدور کوثر→شریعتی و کیس انتقال جدا؛ نتیجه `partial` وقتی هزینه یا دسترسی ناقص است.

**پذیرش:** planner با oracle exhaustive کوچک موافق؛ مسیر با alight قبل از board یا پایان trip تولید نشود؛ terminal و dwell درست؛ confidence از منبع حفظ؛ endpoint قدیمی بدون رگرسیون.

### R2b — نخستین قابلیت عملیاتی ارزشمند A→B محدود

**پیشنهاد محصول:** «برای این سفر در کریدور پشتیبانی شده، گزینه های واقعاً قابل بررسی و دلیل انتخاب را نشان بده»؛ نه routing کل شهر.

**کارها:** انتخاب کریدور با داده ورودی/پیاده/تعرفه معتبر؛ افزودن فقط آن access edges؛ ETA با caveat؛ جمع هزینه فقط با اجزای معلوم؛ یک سؤال قابل رد در صورت تغییر نتیجه. UI کوچک داخل جریان موجود، بدون بازطراحی خانه؛ پس از تأیید جداگانه.

**پذیرش موفقیت:**

- حداقل ۲۰ سفر میدانی جدید و مستقل از داده کالیبراسیون، در جهت/بازه های نمونه گیری ثبت شده؛
- گزارش MAE، صدک ۹۰ خطای مطلق، missed-transfer و خطا به تفکیک کیفیت/نوع روز؛
- آستانه انتشار ETA پیش از جمع آوری داده تصویب شود، نه پس از دیدن نتایج؛ تا آن زمان عنوان آزمایشی و بدون تضمین؛
- برای فاز نامعلوم interval با روش روشن، نه احتمال ساختگی؛
- هزینه نهایی یا unknown صریح؛ هیچ مسیر بدون داده، برنده اقتصادی اعلام نشود؛
- ناشناس و بدون ذخیره پروفایل کار کند؛ تعداد گزینه ها اجباری نباشد؛
- زمان پاسخ deterministic و مصرف حافظه benchmark شود، و رفتار قبلی مترو/بات خراب نشود.

### R3 — ارائه عمومی محدود و کنترل منابع

**کارها:** ثبت route دقیق core، schema ورودی/خروجی، روش POST محدود در edge، error contract، bounded dates/candidates/transfers، timeout، feature flag و inline why.

**پذیرش:** fail-closed قید سخت، منع actor جعلی، تست rate/concurrency، planner بدون تماس provider خارجی برای هر query مترو، rollback بدون تغییر موتور/داده خام.

**بودجه اولیه پیشنهادی برای آزمون، نه اندازه گیری فعلی:** حداکثر horizon یک روز به اضافه همسایه لازم، حداکثر دو تعویض در پایلوت، timeout محاسبه قابل تنظیم و cache محدود. اعداد نهایی با benchmark در محدودیت ۱۹۲ MiB تعیین شوند؛ cache بی سقف مجاز نیست.

### R4 — بسفود روی همان قرارداد

**کارها:** pipeline بازتولیدپذیر، freshness field-level، min-order/stock/quote جدا، retry و expiry، location scope؛ استفاده دوباره آداپتور تپسی بدون تبدیل status به quote. برای Snappfood تا تست پایدار زنده، capability نامشخص/غیرفعال بماند.

**پذیرش:** بدون قیمت تاریخی با عنوان لحظه ای؛ بدون unknown=free؛ لینک به فروشگاه درست؛ منوی خالی fallback؛ بودجه با ارسال فقط وقتی واقعاً محاسبه پذیر است؛ provider outage به Transit سرایت نکند.

### R5 — حافظه تدریجی و قابل کنترل

**کارها:** explicit local preferences با نسخه و حذف/اصلاح؛ سپس یادگیری opt-in محدود؛ بعد از auth، sync اختیاری.

**پذیرش:** «چه می دانی؟»، اصلاح، حذف موردی/همه، توقف یادگیری، scope و expiry؛ نبود پروفایل مانع استفاده نیست؛ تست cross-user access و حذف/لغو رضایت؛ بهبود زمان تصمیم با آزمایش، نه ادعای خودکار.

### R6 — بسپی / shopping

**کارها:** دامنه خرید و شناسه کالا، adapter discovery/quote فروشنده، مقایسه نقد/اقساط هم ارز، referral؛ نه کیف پول یا اعتباردهی از طرف بسراه.

**پذیرش:** مجموع قابل بازتولید با تمام اجزا؛ داده نامعلوم واجد عنوان ارزان تر نباشد؛ دسترس پذیری/صلاحیت از provider؛ handoff واقعی آزمایش شود.

### R7 — اتوماسیون پس از اثبات ارزش دو حوزه

**کارها:** پیشنهاد تکراری → آماده سازی برای تأیید → اجرای محدود؛ سقف هر سفارش/دوره، revoke، idempotency، atomic reservation و audit.

**پذیرش:** بدون مجوز معتبر صفر execution؛ دوبار رسیدن job سفارش تکراری نسازد؛ افزایش قیمت/ابهام نیازمند تأیید؛ نتیجه نامعلوم به عنوان موفقیت ثبت نشود؛ بازیابی خطا و توقف برنامه آزمایش شوند.

## ۱۷. ماتریس تست و مشاهده پذیری

### واحد و property

- comparator: عدم تسلط گزینه بر خودش، یکنواختی dominance، تساوی، unknown در objective مشترک، interval overlap و داده stale؛
- قید: max cost، max walk، arriveBy و حساسیت غذایی؛ violated و undetermined جدا؛
- ترجیح: درخواست فعلی در برابر preference ذخیره شده بدون عبور از gate مجوز؛
- explanation: هر عدد و reason به فکت همان request متصل؛
- question: در دو پاسخ فرضی باید نتیجه واقعاً تغییر کند؛ بدون اثر سؤال تولید نشود.

### planner و داده

- همان ثانیه departure، arrival گذشته ولی dwell فعال، پایانه و برگشت؛
- غدیر در برابر فرودگاه، دو جهت، line1↔line2 و مقصد قبل/بعد؛
- زمان تعویض ناکافی، missed train، آخرین سرویس، نیمه شب و تعطیل؛
- شناسه روزانه تکراری و stop name مشابه با element متفاوت؛
- walking disconnected، entrance نامعلوم، bus بدون timetable؛
- مقایسه الگوریتم با exhaustive oracle روی گراف کوچک و held-out میدانی؛
- hashes، count و pipeline reproducibility غذا/اتوبوس.

### provider و امنیت

timeout، malformed/oversized payload، 429، schema drift، redirect، cancellation، unknown stock، quote منقضی و مقصد متفاوت؛ fake userId/consent، IDOR، body بزرگ، تاریخ خارج horizon، URL غیرمجاز و prompt injection.

### مرورگر/بات و دسترس پذیری

حفظ HM7/CSP، ۳۲۰/۳۶۰/۳۹۰/۷۶۸/۱۴۴۰، دو theme، loading/error/empty/partial، denied/expired location، عدم prompt خودکار نامرتبط، offline، بازگشت، keyboard و touch؛ device sign-off از DOM test جدا. workflow بات با fixture بدون ارسال واقعی و سپس smoke واقعی فقط با مجوز مرحله انتشار.

### مشاهده پذیری کمینه

requestId تصادفی، dataVersion، policyVersion، مدت مرحله، تعداد candidate، result state و reason code خطا؛ بدون مختصات دقیق/نام منزل/متن حساس. سنجه ها شامل:

- latency و timeout جداگانه planner/provider؛
- unknown/stale rate و شکست استعلام؛
- ETA error روی سفرهای واقعاً اندازه گیری شده؛
- هزینه برآورد در برابر پرداخت مشاهده شده و هم ارز؛
- سؤال مفید، انتخاب، بازگشت داوطلبانه و صرفه جویی فقط با baseline معتبر؛
- automation incident در مرحله اجرا، با تعریف روشن و هدف صفر.

داشتن `logger:false` نیاز اندازه گیری را حذف نمی کند؛ instrumentation باید حداقلی و دارای retention مصوب باشد.

## ۱۸. انتشار و بازگشت در مراحل آینده

این بخش دستور اجرای اکنون نیست.

1. تغییرات هر مرحله در diff موضوعی با test evidence و data manifest بازبینی شوند.
2. shadow evaluation بدون تغییر پاسخ موجود؛ مقایسه planner و oracle و عدم اثر بر مترو/بات.
3. feature flag فقط برای کریدور و گروه آزمایش مجاز؛ capability ناقص در UI پنهان یا صریح غیرفعال.
4. backup دقیق artifact/data، استقرار اتمیک/هماهنگ و خواندن دوباره hash/API واقعی.
5. rollback مستقل لایه intelligence؛ API قدیمی و موتور سالم باقی بمانند.
6. حافظه/quote schema آینده دارای migration و برنامه compatibility باشد؛ rollback کد به معنی پاک شدن داده شخصی یا برگشت تراکنش مالی نیست.

هیچ raw CSV برای مطابق کردن تست با خروجی جدید تغییر نکند. خطاهای شناخته شده داده پشت پاسخ LLM پنهان نشوند.

## ۱۹. پرسش های باز برای دروازه های بعدی

این ها مانع تحویل گزارش نیستند و اکنون زنجیره سؤال از مالک شروع نمی کنند. هنگام رسیدن به هر مرحله، فقط سؤال اثرگذار همان مرحله پرسیده شود:

1. کریدور اول با امکان برداشت میدانی تازه کدام است؟ پیشنهاد شروع: کوثر→شریعتی برای station-to-station، سپس access محدود تأییدشده.
2. آیا برای routing مختصاتی، رضایت ارسال موقت به core پذیرفته می شود، یا الزام پردازش کامل روی دستگاه حفظ شود؟
3. تعرفه و قواعد پرداخت/تعویض از چه منبع و با چه تاریخ اثری وارد شود؟
4. معیار موفقیت ETA پیش از آزمایش چه حدی باشد و کدام سفرها از deadline recommendation کنار گذاشته شوند؟
5. برای quote مخصوص مقصد غذا، انتقال مقصد به provider تحت چه رضایت و دامنه ای مجاز باشد؟
6. پیش از subscription، چه baseline قابل اندازه گیری نشان دهد زمان/هزینه واقعی کاربر بهتر شده است؟

**پیشنهاد تصمیم همین مرحله:** تأیید معماری و اجازه R0/R1، نه مجوز R2 تا R7 به صورت یکجا.

## نتیجه نهایی

بِسراه از صفر شروع نمی کند: هسته زمان بندی مترو، API و Mini App، داده ساختاری اتوبوس، کاتالوگ غذا و اتصال محدود provider دارایی واقعی اند. اما «Intelligence Core» مشترک، پروفایل رضایت محور، مقایسه هزینه نهایی و اجرای خودکار هنوز قابلیت فعال نیستند.

مسیر کم خطر و ارزشمند، **شواهد معتبر → قرارداد مشترک → تصمیم قطعی → پایلوت Transit محدود → اتصال بسفود → حافظه اختیاری → خرید → اجرای محدود** است. محصول ابتدا باید بتواند صادقانه بگوید چه چیزی را می داند و چه چیزی را نمی داند؛ سپس از شناخت مجاز کاربر برای بهتر کردن تصمیم استفاده کند، نه صرفاً برای اضافه کردن یک لایه گفتگوی AI.
