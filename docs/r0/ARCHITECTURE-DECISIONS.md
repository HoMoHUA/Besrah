# تصمیم های معماری پذیرفته شده در R0

وضعیت: ثبت تصمیم مالک برای ادامه طراحی؛ این فایل پیاده سازی R1 نیست.

## محدوده مجاز

- R0 شامل تثبیت خط مبنا، checkpoint، بازتولید داده اتوبوس، شناسنامه نسخه و اصلاح دو خطر P0 در راه اندازی و رضایت مکانی است.
- اجرای R1 تا R7 و هرگونه انتشار روی Production نیازمند تأیید بعدی مالک است.
- معماری فعلی Node.js/TypeScript، Modular Monolith، موتورهای سالم، API های موجود، Mini App، بات و HM7 حفظ می شوند.
- هیچ کد جدید Intelligence Core، routing، پروفایل سروری یا اتوماسیون در R0 ساخته نمی شود.

## اصلاح اولویت Preference و Memory

**تصمیم تأیید شده مالک:** Preference و Memory از ابتدای طراحی Intelligence Core جزو قراردادهای اصلی هستند؛ نه الحاقی پس از تکمیل موتور تصمیم.

در اولین مرحله طراحی/پیاده سازی مجاز Intelligence Core باید این موارد لحاظ شوند:

1. ترجیحات صریح و محلی با دامنه روشن، منبع، نسخه و امکان ویرایش و حذف.
2. تفکیک ترجیح نرم از محدودیت سخت و اجازه استفاده فقط در زمینه مجاز.
3. امکان استفاده واقعی نخستین موتور تصمیم از ترجیحات صریح کاربر، بدون وابستگی اجباری به حساب یا حافظه سروری.
4. رابط/مرز Memory با امکان عدم ذخیره، حذف و توقف استفاده؛ تاریخچه بازدید با ترجیح اعلام شده یکسان نیست.
5. ناشناس ماندن و خالی بودن حافظه باید حالت معتبر باشد.

**فعلاً خارج از محدوده:** schema و engine جدید، همگام سازی سروری، احراز هویت، یادگیری رفتاری، embedding/vector DB، ذخیره دائمی مکان، سفارش/پرداخت خودکار.

این تصمیم اولویت طراحی بخش های ۹، ۱۰ و R1 گزارش معماری را تکمیل می کند. استقرار حافظه سروری همچنان مرحله جداگانه است؛ قرارداد Preference و Memory از آغاز R1 در کنار Context/Candidate/Recommendation طراحی خواهد شد.

## قواعد شواهد و داده

- واقعی، تخمینی، نامعلوم و منقضی جدا بمانند؛ مجهول صفر نیست.
- افزوده های قدیمی اتوبوس بدون منبع توقف، با عنوان تأییدنشده حفظ شوند؛ نه حذف و نه رسمی اعلام شوند.
- metadata باید از محتوای واقعی محاسبه شود و pipeline قابل بازتولید باشد.
- شناسنامه نسخه، snapshot کاری، artifact محلی و runtime مستقر را از هم جدا کند؛ HEAD به تنهایی شناسه کامل محصول نیست.
